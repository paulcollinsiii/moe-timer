# Break-eligible timers — multiple "screen" activities

Status: reviewed — all comments resolved, ready for implementation
Branch: `feature/break-eligible`
Predecessor: `20260727.breaktime.plan.md` (non-blocking Screen Break, merged as `92823c5`)

## Problem

The non-blocking Screen Break lets the kid run Piano or Violin during a break.
That is the point of it. But not every extra timer is a genuine break from a
screen: "Laundry folding" is a chore done *with the TV on*. Running it during
an eye-rest break defeats the break, and running it outside a break accrues
real screen exposure that today is invisible to the break scheduler.

So an extra timer needs to declare whether it is a legitimate break activity.

## Decisions (settled in discussion, 2026-07-28)

| Decision | Choice |
| --- | --- |
| Flag name | `break_eligible` (per-timer bool) |
| Polarity | `true` = valid during a Screen Break. Laundry folding is `false`. |
| What it gates | **Startability, not selection.** Every timer stays reachable by Button C; a non-eligible one simply cannot be started while a break runs. |
| Screen-break accrual | A **signed balance**: non-eligible RUNNING time adds 1:1, eligible RUNNING time subtracts 1:1, floored at zero. Idle is frozen. |
| Daily allocation | **Not** debited by non-eligible timers. Accrual tracks eye exposure; allocation tracks entitlement. A chore should not cost TV budget. |
| Break entry | The active timer is forced to PAUSED; selection snaps to slot 0 (break screen). |
| Break exit | Selection returns to the slot the break interrupted, **only when nothing is running**. |

## The model

The unifying idea: **slot 0 is itself `break_eligible = false`.** Screen time is
the original non-eligible activity. Laundry folding is a second one. That
collapses what looks like two systems into a single rule:

> **Screen exposure is a signed balance. Non-eligible RUNNING time adds to it
> at 1×; eligible RUNNING time subtracts at 1×, floored at zero. A break is due
> when the balance reaches the interval, and a Screen Break refuses to start
> any slot that is not `break_eligible`.**

No special-casing of slot 0 in the accrual path, and the existing eye-rest
behaviour falls out unchanged: with no eligible timer ever run, the balance only
rises and behaves exactly as the counter does today.

"Balance" and "accrual" refer to the same quantity throughout: `run_accum_sec`
plus the un-folded live segment. The code keeps the existing names.

### Where the accrual lives

Keep `run_accum_sec` / `run_started_wall` on **slot 0** and let non-eligible
extras drive slot 0's fields. Slot 0 *is* the screen, so this is coherent, and
it costs nothing new:

- `timer_shift_expiry` already shifts `run_started_wall` for every slot
  (`main/timer.c:505`), so NTP correction generalises for free.
- The crash-recovery snapshot already carries both fields
  (`main/timer.c:585`), so no version bump for the accrual change.

The cost is that `timer_run_accum` currently keys off `sl->state ==
TIMER_RUNNING` on the *active* slot (`main/timer.c:424`). That has to become
"a timer is running", keyed on slot 0's `run_started_wall != 0` — slot 0's own
state may be IDLE or PAUSED while Laundry or Violin runs. Slot 0 becomes the
sole owner of the balance; the extras' own `run_started_wall` fields go unused
(harmless — `timer_shift_expiry` keeps shifting them).

The **direction** is not stored. It is derived at fold time from the running
slot's `break_eligible`, which is always available because `timer_defs_install()`
runs before any `timer_*` call. That keeps the snapshot free of a direction bit
and makes the sign impossible to desynchronise from the defs.

This makes the fold points genuinely load-bearing (I10): every transition into
or out of RUNNING now changes the *sign* of the balance, not merely whether it
moves. See G1–G3 for three places that assumption breaks today.

## Behaviour rules

1. `break_eligible` is a compile-time default (Kconfig) overridden by the
   HA-managed NVS blob, exactly like `reloadable`.
2. Slot 0 ("Screen") is permanently `break_eligible = false`. It is not
   configurable.
3. The balance rises 1:1 while the active slot is RUNNING and not
   break-eligible, and falls 1:1 while it is RUNNING and break-eligible.
   Floored at zero — no credit is banked below empty.
4. Nothing running means the balance is frozen. Idle time neither adds nor
   drains.
5. A break may become due while slot 0 is IDLE or PAUSED — the kid can fold
   laundry for the whole interval without ever starting Screen.
6. On break start: the active timer is forced to PAUSED, the interrupted slot
   is recorded, selection snaps to slot 0, the break screen is shown.
7. During a break, Button A is refused on any non-eligible slot. The ▶ glyph is
   not drawn, matching the existing "label shows iff a press would work"
   convention (`main/display_screens.c:203`).
8. During a break, every slot remains reachable by Button C. Swapping to
   Laundry shows its screen and remaining time; it just cannot be started.
9. On break end: chime unless a break-eligible timer is RUNNING (unchanged),
   then return selection to the interrupted slot — only if nothing is running.
10. Slot 0's break-exit state is **PAUSED if `remaining_at_pause > 0`, else
    IDLE**. Derived, not stored.

## Structural invariants

Carried forward from the predecessor plan, extended:

- **I1** Only the active slot can be RUNNING.
- **I2** `TIMER_BREAK` lives on slot 0 only.
- **I3** Slot 0 may be in BREAK while any slot is active.
- **I4** Break helpers read slot 0 explicitly, never the active slot.
- **I5** `timer_break_tick()` latches the end edge; `timer_break_take_ended()`
  consumes it once. Both idempotent.
- **I6** *(new)* A non-break-eligible slot is never RUNNING while slot 0 is in
  BREAK. Guaranteed by rules 6 and 7 — this is what keeps
  `wake_policy_break_chime()` honest without changing it.
- **I7** *(new)* Slot 0 exits BREAK to PAUSED iff `remaining_at_pause > 0`,
  otherwise IDLE.
- **I8** *(new)* The exposure balance moves iff a slot is RUNNING: up when that
  slot is not `break_eligible`, down when it is. It never goes below zero and
  never moves while nothing runs.
- **I9** *(new)* Slot 0's `run_accum_sec` is reset by exactly two things: break
  start and day rollover. No `timer_start` on any slot may clear it (G1).
  Draining to zero via an eligible timer is not a reset — it is arithmetic.
- **I10** *(new)* Every transition into or out of RUNNING, on any slot, folds
  the live segment at the *old* direction before re-arming at the new one. This
  is what makes the sign derivable rather than stored (G2).

## The balance: eligible timers drain it

The scenario that motivates this: fold laundry 15 min, practise violin 15 min,
sit down to watch TV, and the break fires immediately. The kid *was* off screens
for a quarter hour. A counter that only ratchets up cannot express that.

So `break_eligible` stops meaning two loosely-related things ("may run during a
break" and "does not accrue") and starts meaning one: **this activity is time
away from a screen.** Running it during a break is allowed *because* it drains,
and it drains whether or not a break is in progress. One property, one
consequence.

```
balance
  30 ├───────────────── interval ─────────────────  ← break fires here
     │              ╱╲
  15 │        ╱────╯  ╲────╲
     │   ╱───╯              ╲───╲          ╱───
   0 └──┴─────┴──────┴───────┴────┴───────┴──────
        Laundry  idle  Violin  idle   TV (Screen)
        (rising) (flat) (falling)(flat) (rising)
```

**Rate.** 1:1, as you specified. Not tunable — a ratio would need a Kconfig knob,
an HA number entity and a story for what 0.5× means, and there is no evidence yet
that 1:1 is wrong.

**Floor at zero, no banked credit.** Three hours of violin must not buy three
hours of uninterrupted TV. The floor is enforced in two places, because the
in-flight segment is not folded yet:

- at fold time, `run_accum_sec` clamps to 0 after adding a negative segment;
- at read time, `timer_run_accum` clamps its return to 0, so a long eligible run
  reports 0 rather than a negative number to logging, HA and the break check.

**Idle does not drain, and that is deliberate.** Freezing on idle looks stingy
next to the motivating story, but the alternative is strictly worse: the device
deep-sleeps whenever nothing runs, so idle *is* the default state, and decaying
through it would mean the balance almost never survives to reach the interval.
Worse, "paused" and "walked away" are indistinguishable to the firmware — pause
the timer and keep watching and the break evaporates. A running eligible timer is
at least weakly attested; wall-clock idle is not attested at all. Settled.

**Direction changes are a fold point.** An HA edit that flips `break_eligible`
on a *running* slot must fold the segment at the old sign before the new def
lands, or the whole in-flight run is retroactively re-signed.
`timer_reconcile_def` (`main/timer.c:311`) already handles def changes for
running and paused slots and is the natural home for it.

**On the obvious exploit.** A kid can leave Violin running without touching the
violin, and the balance drains. That is unfixable in principle — the device
cannot see the room — and it is the same trust the Screen timer already assumes.
But note the exploit costs wall-clock time at 1:1: dodging a 30-minute break
takes 30 real minutes of not watching TV, which is the outcome the break wanted.
It is self-policing, so do not "harden" it later — a kid gaming it is a
conversation for a parent to have, not a bug for the firmware to fix.

## Anti-gaming (rows 3, 11, 12, 13)

The rule is **a break that has been earned cannot be dodged**. Pressure-testing
rows 3 and 11 against the current code found three places where it can be, all
latent today because accrual only ever belonged to a RUNNING slot 0.

**G1 — `timer_start` zeroes the accrual (`main/timer.c:242`).** `sl->run_accum_sec
= 0` runs on every start. Once accrual lives on slot 0 and laundry feeds it,
starting *any* timer resets the eye-rest clock: fold laundry for 29 minutes,
press A on Piano, and the counter is back to zero. This is the cheapest and most
likely exploit, and a kid finds it by accident.

*Fix:* `timer_start` must not touch `run_accum_sec` at all. The only two resets
are `timer_start_break` (fresh window after a break) and `timer_reset` (day
rollover, via the `memset`). Screen restarting mid-day after a parent grants more
time correctly keeps its accrual — the eyes do not forget.

**G2 — `expire_slot` never folds the run segment (`main/timer.c:305`).** It sets
`TIMER_EXPIRED` and bumps `completions`, nothing else. Today `timer_run_accum`
gates on `state == TIMER_RUNNING`, so the final live segment is silently dropped
at expiry — harmless when the screen timer expiring means screen time is over
anyway. Under this plan it is row 11's exploit: pick a laundry duration that ends
just past the threshold and up to a full laundry run of accrual evaporates. And
if the reworked `timer_run_accum` keys on `run_started_wall != 0` instead of
state (which it must, since slot 0 may be PAUSED while laundry runs), the same
gap inverts into accrual advancing *forever* after expiry.

*Fix:* `expire_slot` folds into slot 0's accrual and clears `run_started_wall`
before setting `TIMER_EXPIRED`. Row 11 then behaves as you expect: the segment
lands, the threshold is crossed, the break fires.

**G3 — `timer_start_break` wipes a paused slot 0 (`main/timer.c:446`).** Task 4
drops the `state != TIMER_RUNNING` guard, which exposes the two lines under it:

```c
int64_t remaining = sl->expiry_wall_time - (int64_t)now;
sl->remaining_at_pause = (remaining > 0) ? (int32_t)remaining : 0;
```

A PAUSED slot 0 has `expiry_wall_time == 0`, so `remaining` is a large negative
number, clamps to 0, and **the kid's banked screen time is destroyed** — the
exact case in row 2 (laundry running, screen paused). Not gaming; the reverse,
and worse.

*Fix:* recompute `remaining_at_pause` only when slot 0 is RUNNING. PAUSED keeps
its value; IDLE already holds 0, which feeds I7's derivation correctly.

**Ordering for row 3.** On a tick wake `maybe_start_break` is called at
`main/main.c:1024`, *before* the `timer_tick` at `:1050` that detects the expiry.
So when both are pending in one wake the break wins, `enter_deep_sleep()` runs,
and the expiry alert is skipped entirely — laundry gets paused at 00:05 and the
alert lands minutes later when the kid resumes. That is the opposite of the
ordering you asked for.

*Fix:* `fire_expiry_alert()` returns (it repaints the main layout at
`main/main.c:586`), so a second `maybe_start_break(now)` after the render switch
at `main/main.c:1076` gives expiry-then-break in one wake. It is a no-op unless
`timer_break_due`, so it costs nothing on every other path. The button path
already has this shape in `finish_or_break` (`main/main.c:520`).

**What is *not* gaming, and stays allowed.** Pausing below the threshold holds
the balance — no exposure, no movement. Running an eligible timer drains it,
which is the feature, not a hole. Deep sleep across the threshold is wall-clock
based and self-corrects. None of these buy screen time for free.

## New persistent state

One byte, and it is the only place the "no new state" instinct does not hold:

```c
uint8_t break_interrupted_slot;  /* slot active when the break started */
```

Rule 8 needs it — once the selection snaps to 0 at break start, nothing else
records what was interrupted. It lives in `rtc_state_t` and therefore bumps the
crash-recovery snapshot version (v5 → v6). Restore validation must reject a
value ≥ `TIMER_SLOT_COUNT`.

## Migration cost

`TIMER_DEFS_BLOB_VERSION` goes 1 → 2 (`include/nvs_config.h:83`). Version or
size drift reads as stale and falls back to the Kconfig table
(`main/timer_defs.c:56`), so **every device with HA-edited timer names or
durations silently reverts to the compile-time table on first boot after
flash.** Hand-set `sdkconfig` names come back correctly; anything edited from
Home Assistant afterward is lost. Acceptable for a single-device deployment,
but it should be a deliberate call, not a surprise.

`DISC_SCHEMA_VER` in `main/mqtt_ha.c` must also be bumped (14 → 15) or neither
the per-timer toggle nor the exposure sensor will appear in Home Assistant. One
bump covers both (task 13).

## Open / deferred

- **Bounded by duration, except on reload.** "Laundry folding" is a timer, so one
  run is capped at its own duration — that is the earned-by-the-chore intent and
  it is not a loophole. The one unbounded edge is `reloadable`: Button B is
  allowed without ParentTesting when `def->reloadable` is set
  (`main/timer.c:143`), so a reloadable non-eligible timer can be re-earned
  without doing the chore again. **Configure non-eligible timers with
  `RELOADABLE=n`.** No code change; worth a line in the docs task.

- **Bedtime needs no new logic — verify, don't build.** Everything you described
  already falls out:
  - Break-crosses-bedtime skips straight to Bed Time via
    `bedtime_break_would_cross` (`main/main.c:559`), which sits inside
    `maybe_start_break` and is source-agnostic. A laundry-driven break inherits
    it the moment task 11 lands.
  - `bedtime_engage` pauses whatever is RUNNING (`main/main.c:502`), and I1 says
    only the active slot can be, so the pause is complete for eligible and
    non-eligible timers alike.
  - `bedtime_should_alert` (`main/bedtime.c:29`) alerts on RUNNING, BREAK, or a
    background break — so an eligible timer running up to bedtime fires the
    bedtime screen, as you want.

  The accepted consequence stands: bedtime can fire up to one break duration
  early. Add two tests (non-eligible break crossing bedtime; eligible timer
  running into bedtime); no production change.

- **Accrual reset is settled.** Slot 0's balance is "how much screen exposure has
  there been", one counter regardless of source, so `timer_start_break` resetting
  it (`main/timer.c:451`) is correct no matter which slot drove it. This is the
  same field G1 protects: break start and day rollover reset it, nothing else.
  Needs the test, not a decision.

- **No on-device balance readout.** The panel does not show it and will not —
  the space is not worth it. HA carries the signal instead (task 13).
