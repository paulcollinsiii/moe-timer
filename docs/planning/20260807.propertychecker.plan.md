# Property checker — a second comparator for the sweep engine

Status: **deferred, not started.** Split out of task 15 of
`docs/planning/implemented/20260729.refactormain.plan.md`, which was written as "generalise the
differential sweep into a reusable engine". That framing is wrong, or at least
too narrow, and this file records why before anyone builds the wrong thing.

## The reframing

Task 15 assumed the sweep's value is diffing old code against new — i.e. that it
is a refactor tool. It is not, or not only. The structure says so: in each cycle
script the comparator is

```c
static int same(const run_t *a, const run_t *b) {
    if (a->n != b->n) return 0;
    for (int i = 0; i < a->n; i++) {
        if (a->ev[i].ev != b->ev[i].ev || a->ev[i].a != b->ev[i].a ||
            a->ev[i].b != b->ev[i].b || a->ev[i].c != b->ev[i].c) return 0;
    }
    return 1;
}
```

Seven lines, pure, called once per case. **Everything expensive — the input
enumeration, the effect tracing, the driver — is independent of it.** Each
cycle's enumeration is ~1000 lines of generated harness and is the real asset.
The comparator is nearly free.

So the deliverable is not "make the diff reusable". It is: **keep the
enumeration, add a second comparator that takes ONE trace and asserts a property
of it.** That turns a one-shot refactor proof into a standing property checker,
and it changes what the engine can find.

## Why this is worth doing — measured, not argued

Two facts established on 2026-08-07 against `59c3afa`:

**1. The sweep is strictly more sensitive than the whole host suite.** BUG-3's
mutant is one token — add `BTN_D` to the tick-drain mask in
`wake_flow_handle_timer_tick()`. Applied to the real source:

| Detector | Result |
|---|---|
| Host suite (34 suites, ~1389 unity cases) | **34/34 pass** — blind |
| `cycle11` sweep | **5120 / 121504 divergences** — killed |

Not a function move; a semantic change to a bitmask. The reason is the whole
argument for this plan: the sweep compares **full ordered effect traces
including arguments**, so it asserts on effects nobody thought to assert on.
BUG-3's own entry notes the only residual difference is "one extra
side-effect-free `timer_get_state()` read" — no unit test asserts on that read,
but the trace records it. Unit tests check what you predicted; the trace checks
what happened.

**2. The enumerated space already contains bugs the comparator cannot report.**
`cycles/cycle11_handlers.py:1051` already enumerates a latched `BTN_D`,
including `(1u << BTN_A) | (1u << BTN_D)` and `0xF`. A latched D is fed through
121504 times per harness. Diff mode cannot report it because old and new drop it
identically — a shared blind spot is invisible to a differential test by
construction.

An invariant would report it immediately. The one that matters here:

> **Conservation of presses** — every latched press is either dispatched or
> explicitly discarded by a named site; none is silently dropped.

That single oracle covers **BUG-2**, covers **BUG-3**, and is **exactly BUG-1's
open fork** ("is the press latched at all during the network window"). Three
tracked entries, one property, and it needs no baseline commit at all.

Other invariants worth encoding once the seam exists:

* every wake ends in exactly one `enter_deep_sleep()`
* `timer_run_accum` is monotone within a RUNNING segment
* the day boundary is crossed at most once per enumerated day
* no render is emitted after the sleep prologue begins

## Second use: the baseline need not be "before the refactor"

Point `BASE` at a release tag rather than a refactor commit and the same engine
becomes a behavioural regression gate for feature work.

It also strengthens fix verification. `refactor.bugdiscoveries.md` currently asks
only that a fix "flip its pinning test deliberately, not silently". A sweep gives
the **complete set of changed cases**, so a BUG-2 fix can be checked to have
changed only not-RUNNING A-press cases and nothing else. That is a much stronger
claim than one flipped assertion.

## Limits — what this will NOT buy

Recorded so the plan is not oversold:

* **The vararg log-stub landmine is invisible to it.** Both sides are host
  builds, so a call skipped by `#define ESP_LOGI(tag, ...) ((void)(tag))` is
  skipped identically in both. See the landmine entry in
  `refactor.bugdiscoveries.md`.
* **`main.c` is unreachable** — it has no host build at all.
* **It will not settle BUG-1.** BUG-1's open question is sync-wake
  *specificity*, which lives in real `net_win` task timing the harness does not
  model. An invariant can confirm a press is dropped; it cannot explain why only
  after a sync.
* **Diff mode is not an oracle.** If old and new are both wrong, the control
  reads 0. Only invariant mode fixes that — which is the argument for doing this
  rather than tidying the existing scripts.

## Prerequisite

**BUG-4 must be fixed first or as part of this.** The cycle generators pin an
absolute `REPO` path to a temporary worktree, so the sweeps currently report a
false PASS when invoked from anywhere else, and become unrunnable once that
worktree is deleted. Building a property checker on top of a harness that tests
the wrong directory would inherit the defect. See BUG-4 in
`refactor.bugdiscoveries.md` for the demonstration and the fix constraint.

## RESEARCH FIRST — do not build before checking this

This is a solved problem shape in general, and hand-rolling ~1000 lines of
enumeration per area is expensive. Before writing any engine code, establish
whether an existing tool already covers the use case for **C, on host, with
ordered effect traces**. Specifically worth checking:

* **Property-based testing for C** — `theft`, `rapidcheck` (C++ but usable from
  a C shim), `libfuzzer`'s structure-aware mode with a custom mutator. Question
  to answer: can any of them express *ordered effect-trace* properties, or do
  they only do input→output? That is the discriminator — this codebase's
  properties are about the SEQUENCE of side effects, not a return value.
* **Model checkers / explicit-state exploration** — TLA+ or Alloy for the state
  machine itself (would need a separate model, so it checks the design, not the
  code), and CBMC / ESBMC, which run on the real C and could in principle prove
  the invariants above exhaustively over bounded inputs. CBMC is the closest fit
  on paper and should be evaluated first.
* **Deterministic simulation / record-replay** frameworks, which are the
  same idea as the current harness and may supply the driver for free.
* **Mutation testing tools for C** (`mull`, `universalmutator`) — orthogonal but
  related: they would tell us which existing assertions are weak, which is how
  BUG-3's blind spot was found by hand in cycle 11.

Record the finding either way. "We checked and nothing fits, here is why" is a
valid and valuable outcome — the current harness is already working and
bespoke-but-understood beats a dependency that almost fits. But that conclusion
should be reached deliberately, not by default.

## Sizing

Unknown until the research above lands. The cheap version is one new comparator
plus one invariant on the EXISTING cycle11 enumeration, which would immediately
give a real answer on BUG-2/BUG-3 for a small fraction of the cost of a general
engine. Consider doing that spike first regardless of the tooling decision — it
tests the whole premise of this plan against a known-answer case.
