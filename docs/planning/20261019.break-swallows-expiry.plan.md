# A break due at expiry swallows the expiry alarm — plan

Owner report 2026-10-19, testing timer: chore-free 45 min and a 45 min
break interval. The timer expired (expiry alarm), and on the next one-minute
wake the screen-break alarm fired too. Owner decision: when both fall due at
once, the **break swallows the expiry** — one alarm, the break's. **Exact
ties only** (option 1): a break that comes due earlier in the final minute
keeps today's behaviour (break first; the remaining seconds run after it).

## Cause

- `wake_flow_watch_final_minute()` (`main/wake_flow.c` ~2461-2495) checks
  `timer_break_due()` only inside `while (rem > 0)`. With a cap equal to the
  interval, run_accum reaches the interval at the same second the expiry
  wall is reached, so the loop exits first and `wake_flow_fire_expiry_alert()`
  runs.
- `timer_break_due()` deliberately does not require RUNNING (`main/timer.c`
  ~776-783: eye rest continues after the day's allocation is spent), so the
  break is still owed and the next wake starts it: two alarms a minute
  apart.

## Decisions — settled, do not re-litigate

1. **Rule:** at the RUNNING→EXPIRED transition, if a break is due at that
   instant (breaks enabled and `timer_break_due(now, interval)` true), start
   the break (`wake_flow_maybe_start_break`) instead of firing the expiry
   alarm. Slot 0 is EXPIRED underneath; the break returns it to EXPIRED and
   **no expiry alarm plays afterwards**. If `wake_flow_maybe_start_break`
   declines (returns false), fire the expiry alarm as today. Its bed-time
   branch (a break that would cross bed time engages the bed-time lock,
   no return) also swallows the expiry; that is accepted.
2. **Every expiry site**, not just the final-minute watch: the final-minute
   watch's post-loop expiry, the button wake's `WAKE_RENDER_EXPIRY_ALERT`
   (~2626), the post-window reconcile (~2710), and the ordinary wake's
   `WAKE_RENDER_EXPIRY_ALERT` (~3216), so a late wake that finds both due
   also gets one alarm. Grep for every other `wake_flow_fire_expiry_alert`
   caller and decide each explicitly in the notes.
3. **The decision is host-tested policy**, not an inline `if` repeated four
   times: put the "expiry or break" choice in one place (a `wake_policy`
   function or a single `wake_flow` helper that the four sites call), with
   unit tests. `main/main.c` gains no line.
4. **Near misses unchanged:** a break due before the expiry instant is
   already started by the final-minute loop; keep that. A break that would
   only come due after expiry (accum below the interval at expiry) is not
   pulled forward.
5. **The break end must not alarm.** When the swallowed break ends, slot 0
   is EXPIRED and was EXPIRED when the break began: `wake_policy_render`
   (or whatever decides `WAKE_RENDER_EXPIRY_ALERT`) must not treat the
   break end as a fresh RUNNING→EXPIRED transition. Prove it with a test;
   fix it if it would alarm.
6. **Persistence:** EXPIRED is persisted before the break starts (the
   existing at-transition save in `wake_flow_fire_expiry_alert` exists so a
   reset mid-alert does not replay the final minute; the swallow path needs
   the same guarantee — `wake_flow_maybe_start_break` already persists
   BREAK; check that an EN reset mid-break restores BREAK→EXPIRED, not
   RUNNING).
7. **Stats publish:** the expiry currently owes an event publish (the
   stats-publish-events work). The swallow path must still owe one (the
   timer did expire), ordered after the break's paint and alarm, as the
   break-start path already orders its own.
