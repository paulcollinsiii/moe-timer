# Stream F2 notes: ESP-IDF v6.0.1 to v6.0.3

Branch `chore/idf-updates`. Scope: IDF only. No managed component moved
(`espressif/mqtt`, `network_provisioning`, `json_generator`, `lvgl` stay);
`dependencies.lock` differs only in its `idf` entry.

## Procedure

1. Confirmed the tag exists: `git ls-remote --tags https://github.com/espressif/esp-idf.git v6.0.3`.
2. Captured the v6.0.1 baseline first (build, `idf.py size`, `idf.py size-components`).
3. `sdkconfig` snapshots in `~/magtag-sdkconfig-snapshots/`: `sdkconfig.pre-f2-bump`,
   `sdkconfig.pre-f2-v601-built`, `sdkconfig.pre-f2-reconf`, `sdkconfig.pre-f2-build`.
4. In `~/esp/esp-idf`: `git fetch --depth 1 origin tag v6.0.3`, `git checkout v6.0.3`,
   `git submodule update --init --recursive --depth 1`, `./install.sh esp32s2`.
   `idf.py --version` reports `ESP-IDF v6.0.3`. The Python env name (`idf6.0_py3.10_env`) is unchanged.
5. `.devcontainer/Dockerfile` pin and comment changed to v6.0.3 (same clone flags).
6. `idf.py reconfigure`, then diff against the snapshot (below), then `idf.py build`.

## sdkconfig diff, every line

The owner's `sdkconfig` kept its values, but only because an existing line wins
over a changed Kconfig default (policy "use sdkconfig"). Three v6.0.3 defaults
differ from what this device runs, and a fresh config (new clone, no `sdkconfig`)
would have taken them:

- `CONFIG_ESP_INT_WDT_TIMEOUT_MS`: v6.0.3 `esp_system/Kconfig` has
  `default 800 if SPIRAM`; v6.0.1 and v6.0.2 had `800 if (SPIRAM && IDF_TARGET_ESP32)`.
  This board DOES enable SPIRAM (`CONFIG_SPIRAM=y` in `sdkconfig.defaults`, 2 MB on the
  2025 MagTag, `SPIRAM_IGNORE_NOTFOUND=y`, `SPIRAM_MEMTEST=n`). The earlier statement
  "this board has none" was wrong. Nothing in `main/`, `components/`, `include/` or
  `test/` reads the value. The Kconfig help gives no reason for the raise, and this
  checkout is shallow, so the upstream commit rationale could not be read. A plausible
  cause (longer cache-off windows around flash and PSRAM writeback) is a guess, not
  evidence. OWNER DECISION (2026-11-14): 800. `sdkconfig.defaults` pins 800 and the
  owner's `sdkconfig` line was set to 800 to match (an unmarked line would otherwise
  keep 300).
- `CONFIG_MBEDTLS_CERTIFICATE_BUNDLE_CROSS_SIGNED_VERIFY`: v6.0.1 and v6.0.2 default n;
  v6.0.3 defaults y, and it selects `CONFIG_MBEDTLS_X509_TRUSTED_CERT_CALLBACK`. The firmware
  never calls `esp_crt_bundle_attach` (grep over `main/`, `components/`, `include/` finds
  nothing; OTA pins `certs/ota_ca.pem`), so the flip is size and about 1 KB of transient
  handshake heap, not behaviour. `sdkconfig.defaults` now pins n; nothing else selects
  `X509_TRUSTED_CERT_CALLBACK` (only that one symbol and its own definition mention it
  in the IDF Kconfigs), and it falls to n by itself.
- `CONFIG_HTTPD_MAX_REQ_BODY_LEN_KB`: the v6.0.3 GitHub release notes list it as a breaking
  change, but the tagged tree has no such symbol. What exists is a rejection of
  Content-Length above UINT32_MAX (413) in `components/esp_http_server/src/httpd_parse.c`
  (~372-385). Setup-mode impact is nil for sane clients; no symbol to set.

Proof, no change to the project `sdkconfig` or `build/`: a fresh config was generated
from `sdkconfig.defaults` in a scratch build dir (`idf.py -B <scratch> -D
SDKCONFIG=<scratch>/sdkconfig.fresh reconfigure`) and diffed against the owner's
`sdkconfig`. The three symbols now agree (`ESP_INT_WDT_TIMEOUT_MS=300`,
`CROSS_SIGNED_VERIFY` and `X509_TRUSTED_CERT_CALLBACK` not set). The remaining differences,
none caused by v6.0.3:

- `CONFIG_IDF_INIT_VERSION`: 6.0.1 in the owner's file (records the version first configured).
- Hand-set `CONFIG_MAGTAG_*` values: timer names/minutes/flags, alert volume, quiet start,
  bedtime, OTA URL.
- The coredump block (`ESP_COREDUMP_*`, the `ESP32_*COREDUMP*` aliases) and, following from
  it, `FREERTOS_ISR_STACKSIZE` (1536 fresh, 2096 owner) and
  `FREERTOS_TASK_FUNCTION_WRAPPER=y`: the owner hand-set coredump-to-flash.

The `Kconfig default value: 1536, sdkconfig default value: 2096` note for
`FREERTOS_ISR_STACKSIZE` remains on every build, for that reason. The two notes for the
watchdog and the cross-signed option are gone (those lines are now unmarked pins).
The two CMake warnings a build prints are: `build.cmake:695` (the component manager's
"re-run" exit code, printed with an empty body) and `project.cmake:786`
("Missing kconfig option. Re-run the build process..."), the normal first-pass retry.
Neither is a compiler warning.

Required step whenever the IDF version moves: diff a fresh config (as above) against
the existing `sdkconfig`, because an old `sdkconfig` hides every changed default. Each
difference is either a hand-set value, or a default to pin in `sdkconfig.defaults`
or accept on purpose.

Before the bump, the first `idf.py build` on v6.0.1 already dropped the
`CONFIG_MAGTAG_FONT_SET*` lines (4 symbols over 8 lines) (their Kconfig belongs to another branch). Expected, not a defect.

## USB CDC `linker.lf` finding

Re-checked in the v6.0.3 tree (`components/esp_usb_cdc_rom_console`):

- `linker.lf` places the console functions (including `esp_usb_console_interrupt`)
  in noflash only `if ESP_CONSOLE_USB_CDC_SUPPORT_ETS_PRINTF`. It still does not list
  `esp_usb_console_available_for_read` or `esp_usb_console_write_available`,
  which the ISR calls (`usb_console.c:213,218`). The bug is therefore unfixed in v6.0.3.
- `usb_console.c:87`: `ISR_FLAG` is `ESP_INTR_FLAG_IRAM` with the symbol y and `0` with n.
  With n the ISR is masked during cache-off windows, so the fault cannot occur.
- The v6.0.1 link map shows both functions and the ISR in flash text (0x4008xxxx range) with n,
  consistent with the above.

Conclusion: `CONFIG_ESP_CONSOLE_USB_CDC_SUPPORT_ETS_PRINTF=n` stays. The comment at
`sdkconfig.defaults` was rewritten to describe the v6.0.3 state.

## Owner notes

OTA delivers app-side fixes only. The bootloader at 0x1000 is never rewritten by OTA, so
OTA-updated devices keep the v6.0.1 bootloader until one USB `idf.py flash`. An old
bootloader with a new app is a supported combination within v6.0.
