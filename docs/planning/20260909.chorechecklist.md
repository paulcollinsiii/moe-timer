# Chore checklist — completion-gated screen time

Status: **draft, third pass.** Review rounds of 2026-09-09 and 2026-09-10 are
folded in and every fork is settled. Section 8 holds the two details that need
hardware rather than a decision.
Branch: `feature/chore-checklist-plan`
Predecessors: `implemented/20260727.breaktime.plan.md` (non-blocking Screen
Break), `implemented/20260728.breakeligible.plan.md` (screen-exposure balance).

## Problem

A daily list of chores should stand between the kid and the day's screen time.
The device already tracks *how long* things ran; it has no notion of a thing
being **done**.

The opening framing was "chores must be acknowledged before a screen break is
over". That framing has a hole the request itself names: with a 60 min
allocation and a 30 min break interval the day contains exactly **one** break,
so exactly one enforcement point, worth exactly the tail of the day — and with
an allocation at or below the break interval there is **no** break and
therefore **no** enforcement point at all. The lever is attached to an event
that may not happen, and whose value varies with when it happens.

So the real problem is: *find a point in the day that always exists, where the
kid always wants something, and hang the chores off that.*

## Decisions (settled in review, 2026-09-09 and 2026-09-10)

| Decision | Choice |
| --- | --- |
| **The gate** | **Split allocation.** The day's first `chore_free` minutes are unconditional; the remainder is withheld until every chore is acked. Not a break extension. |
| **Per day type** | `chore_free` is **four** settings — weekday / weekend / holiday / summer — mirroring the existing allocations. A weekday can be 100 % gated while the weekend keeps its morning cartoons. |
| **List size** | **3 chores**, hard cap. Screen-gating chores are quick hits. One button per chore, one screenful, no refill, no paging. |
| **Authoring** | A `chores` array in the retained bulk config document (document-only, like `holidays`), with an HA To-do List as the optional UI over a one-automation bridge. |
| **Buttons** | **Wholesale remap.** A = Mode (Timers ⇄ Chores) on every screen; B = Start/Pause; C = Next timer; D = Refresh. In Chore mode B/C/D toggle chores 1–3. |
| **`PARENT_TESTING`** | **Retired outright**, along with the old Button-B reset mapping. Reload moves to B on an EXPIRED slot. |
| **Reachability** | Chore mode is refused while a timer is RUNNING. You cannot tick off dishes while the TV clock runs. |
| **Ack authority** | **The device, solely.** HA is a read-only mirror. No parent ack, no un-ack from HA, no conflict rule. B/C/D **toggle**, so a mis-press is fixed on the device. |
| **Ack identity** | Positional bits + a list-hash invalidation. A list edit clears the acks; they are re-acked, which is cheap at three. |
| **Ack feedback** | **The NeoPixels**, red → green per chore, with the panel following behind. **No sound.** |
| **Gate indication** | **In the Screen progress bar**: the locked amount is a block held at the **left**, and the free tranche drains to the right of it. |
| **Release visibility** | **Not in the parenthetical.** The `(±n min today)` line is reserved for the screen-adjust field, so the release must not write `adjust_today_sec` (§5.2). The release is very much *visible* — the locked block vanishes and the bar goes full width — just not there. |
| **Mode reverts** | **Day rollover only.** Never on the final ack: a mis-press must not cost a trip back through the mode button. |
| **A bad config** | **Blocks the device** with its own screen, charge-lock style. An unignorable alert beats an ack nobody reads. |
| **HA entities** | Per-chore, same logic as the custom timers. |
| **HA dashboard** | **In scope.** A shipped dashboard YAML — a config view and a reporting view — because the settings count has outgrown the default device page. |

## 1 · Authoring the list in Home Assistant

### 1.1 Why not four text entities, and why not one text box

Timers 1–4 are four entities because each carries four *typed* fields (name,
minutes, reload, break) that HA renders as a number and two switches. A chore
carries one field: its name. Four text boxes to type three strings is the worst
of both — a rigid cap and a fiddly UI.

A single multi-line text box is tempting and does not work as well as it reads:

- The MQTT `text` platform has `mode: text | password`. There is no textarea.
  A newline is not enterable in the HA UI field, so "one task per line" is
  really "one task per line, if you publish it from a script" — which is the
  bulk document, below, with extra steps.
- HA caps a `text` entity at **255** characters. This firmware caps a
  `set/<key>` value at **`CFG_STR_MAX` = 128** (`include/config_validate.h`),
  and the failure mode at the boundary is a silently truncated list.

### 1.2 The store: a `chores` array in the bulk config document

The same shape and the same durability story as `holidays`, which is already a
document-only field:

```json
{
  "ver": "20260909",
  "chores": ["Dishes away", "Trash out", "Homework"]
}
```

Document-only is legitimate here. The architecture's durability rule
(`docs/architecture.md`, "Config channels") runs one way: anything settable
**from an entity** must also be expressible in the document, because a retained
`set/` is consumed on apply and an entity-only field is destroyed by the next
document apply. It does not require the converse. `holidays` is the precedent —
and since acks are device-owned (§1.4), nothing about a chore is
entity-settable at all.

| Cap | Value | Why |
| --- | --- | --- |
| `CHORE_MAX` | **3** | One per ack button, one screenful, one NeoPixel, no refill logic, a 3-bit ack mask. |
| `CHORE_NAME_MAX` | **20** chars | The panel's 16 pt budget on a 296 px row with a tick column. |

Enforced with a **named error in the `config_ack`**, never truncated: a fourth
chore is an `errors` entry. At 3 × 20 the whole array is ~70 B of the 2048 B
`CONFIG_BUF_MAX` (`main/mqtt_ha.c:55`), which is comfortable beside a full
holiday list — the ceiling that worried the first draft is a non-issue at this
cap.

### 1.3 The optional To-do List bridge

HA's To-do List integration gives a real checklist card — add/remove/reorder on
the phone — and one automation publishes it to the device:

```yaml
automation:
  - alias: "MagTag — publish chore list"
    triggers:
      - trigger: state
        entity_id: todo.daily_chores
      - trigger: homeassistant
        event: start
    actions:
      - action: todo.get_items
        target: { entity_id: todo.daily_chores }
        data: { status: needs_action }
        response_variable: items
      - action: mqtt.publish
        data:
          topic: magtag/xxxxxx/config
          retain: true
          payload: >
            {"ver": "{{ now().timestamp() | int }}",
             "chores": {{ items['todo.daily_chores']['items']
                          | map(attribute='summary') | list }}}
```

`ver` moving on every edit is deliberate — `config_apply` applies a document
only when `ver` differs from the stored `cfg_ver`.

Two caveats before anyone builds it. A real bulk document also carries
`holidays`, four `timers` entries and every scalar, so this automation must
publish the **whole** document, not just the chores field — template the rest in
beside it. And a to-do list with four open items is rejected wholesale rather
than trimmed, so the template should slice to three or the `config_ack` will
carry the rejection every time.

This is a convenience, not the contract. Publishing the document by hand, or
from any script, is equally supported.

### 1.4 What HA gets back — read-only, and that is the whole design

**The device is the sole authority on acks.** HA displays them and never writes
them. This deletes an entire problem the first draft spent a section on: an
MQTT `button` entity publishes once, non-retained, and this sleeping device
would never see the press — so a parent override would have needed a retained
`set/` or a `cmd` document, with a conflict rule behind it. None of that is
needed. If the acks are being gamed, that is a conversation to have with the
kid, not a race to win over MQTT.

Mis-presses are handled on the device: B/C/D **toggle**, so an accidental ✓
comes straight off (§2.4).

Published in the existing stat payload, read-only:

- `sensor.magtag_xxxxxx_chores_left` — count outstanding (Primary).
- `sensor.magtag_xxxxxx_chores_done` — count acked today (Diagnostic).
- One `binary_sensor` per chore, named from the list — the same treatment the
  custom timer slots already get, and with the same known cost: a chore rename
  is a discovery republish plus an orphaned recorder series.

Recorder history on those is the parent's audit trail, free: "Homework acked at
16:04, three minutes after school" is a conversation the device enabled without
pretending to police anything.

Two mechanical requirements follow. `STATS_JSON_DISC_SCHEMA_VER` in
`include/stats_json.h` must be **bumped** — a new entity does not appear at all
until the retained discovery documents are republished. And chore names must
join `ha_config_discovery_hash()`, exactly as the timer slot names already do,
or a rename leaves HA showing the old name until the next schema bump.

## 2 · Buttons: the mode remap

### 2.1 Why the layout has to move

There are four buttons and all four are taken (A start/pause, B reset, C swap,
D sync). Every scheme that keeps that layout and adds a chore screen ends up
overloading a key — the first draft had Button C meaning "ack #3, except when
it means exit", which is unexplainable to the person actually using it.

The way out is to stop treating the four buttons as four actions and treat one
of them as the **mode**:

| Button | Timer mode | Chore mode |
| --- | --- | --- |
| **A** | **Mode → Chores** | **Mode → Timers** |
| **B** | Start / Pause / Resume / Reload | Toggle chore **1** |
| **C** | Next timer | Toggle chore **2** |
| **D** | Refresh + force sync | Toggle chore **3** |

A means the same thing on every screen in both modes, which is what makes it
learnable and what leaves room for a third mode later. This is the reason the
remap is worth its cost even on a device with no chores configured — the chore
list is the first mode, not the justification for the concept.

### 2.2 What the remap costs

It is a breaking change to muscle memory: A has been start/pause since the
device existed, and the household will mispress for a week. That is the price,
it is paid once, and it is why this lands as its own phase (§6) rather than
buried inside a feature.

Mechanically it touches `button_actions.c`, `buttons_policy.c` (the EXT1 wake
mask), `wake_flow.c`'s dispatch matrix, both display modules, and **~10 of the
16 goldens** — every screen with a button row. Regenerate deliberately with
`MAGTAG_WRITE_GOLDEN=1`, which rewrites *every* golden, then check out the ones
that did not intend to change.

### 2.3 Retiring `PARENT_TESTING`, and where Reset goes

`CONFIG_MAGTAG_PARENT_TESTING` goes with the old B mapping. Its footprint is
wider than it looks and all of it is deletion: `main/Kconfig.projbuild`,
`sdkconfig.defaults:124`, the macro pair in **`main/main.c:89-92`** (a rare
change that *removes* lines from the composition root), the macro block plus
three call sites in `wake_flow.c` (`:179`, `:424`, `:810`), one in `buttons.c`,
the `reload_allowed` comment in `buttons_policy.h`, three assertions in
`test_wake_flow` (`:1972`, `:2097`, `:2817`), and an entire dedicated suite —
`test/test_wake_flow_parent`, built with
`EXTRA_DEFS CONFIG_MAGTAG_PARENT_TESTING=1` at `test/CMakeLists.txt:69` — which
is deleted outright. `timer_reload_allowed(bool)` loses its parameter.

Shipped devices are unaffected: `sdkconfig.defaults` carries `=y` but the
hand-maintained `sdkconfig` sets it `n`, so this changes the default build only.

**But `reloadable` extra timers also use Button B**, and that is a live shipped
feature — it is what the `Meditation (x2)` completion counter exists for. It
needs a home, and there is a clean one that adds no button:

> B is Start / Pause / Resume — and on an **EXPIRED** slot, where B has no job
> at all today, B is **Reload** when the slot is reloadable.

Same key, no mode, and arguably better than today: you press the same button to
go again. Screen (slot 0) has no def and is never reloadable, so a kid still
cannot reset their own screen timer — the property `PARENT_TESTING=n` was
protecting is preserved by construction rather than by a build flag.

What is genuinely lost is the parent's on-device reset of the Screen timer. The
HA screen-adjust number already covers it.

### 2.4 Chore mode

Reachable only when chores are configured and **no timer is RUNNING** — see
§4.2. Acks **toggle**, so a mis-press is undone by pressing the same button
again.

```
┌──────────────────────────────────────────────────┐
│  CHORES                                  1 of 3  │
│                                                  │
│  ✓  Dishes away                                  │
│     Trash out                                    │
│     Homework                                     │
│  Timers      ✓ 1         ✓ 2         ✓ 3         │
└──────────────────────────────────────────────────┘
```

Three fixed rows. Nothing slides, nothing refills, the row order never changes —
which is what makes B/C/D unambiguous, what a 3-chore cap buys, and what lets
the NeoPixels mirror the rows one-for-one (§2.5).

On the last ack the header becomes `3 of 3` and the count line reads
`Screen time unlocked` — the mode does **not** bounce you out (§4.2), so the
screen has to say that something happened.

Rejected: **long-press to enter a chore mode.** It needs hold detection that
does not exist today (`buttons.c` is a 10 ms debounce plus a NEGEDGE latch;
only the held-through-sleep guard is level-based), and it is undiscoverable on
a device with no manual. The mode button makes it unnecessary.

### 2.5 Ack feedback is the NeoPixels, not the panel and not a sound

An ack is a state change, so under today's policy each one is a **full**
refresh — ~3 s, and ~9 s to tick three boxes. Even a partial is not the 0.4 s
it sounds like:

| Component | Cost | Whose layer |
| --- | --- | --- |
| Partial refresh | ~0.4 s | driver |
| Ghost-clean double pass (inverted band, 1.1 s wait, true frame) | ~1.5 s | **display.c policy** |
| Minimum-interval guard between refreshes | 1 s floor | **ssd1680 driver** |

So a naive partial is ~1.9 s and three acks still cost ~6 s. The panel is never
going to be the fast path here. The fix is to **stop making it the feedback
channel**:

> Three of the four NeoPixels map to chores 1–3: **red = outstanding, green =
> done.** The fourth carries the gate itself — red while time is locked, green
> once it is released.

Sequencing, which is where the feel lives:

1. A **button wake** lights the pixels in their **pre-press** state first, so
   you see what the device thought before you touched it.
2. ~400 ms later the pressed chore's pixel flips **red → green**. The
   transition is the acknowledgement.
3. The panel's partial runs **behind** that. The pixels cover the panel's
   latency instead of competing with it, which is what makes ~1.5 s of e-ink
   feel like nothing.
4. **Subsequent presses in the same awake window flip instantly** — no
   pre-state pause. You already saw the starting state.
5. **Pressing one row twice undoes it, within the same wake.** Added
   2026-09-23 from the board: *"if I misclick and want to put the state back"*.
   A tick is a toggle and a toggle is its own inverse, so this needs no new
   semantics — but it does need the device to count two presses as two, which
   is clause 6.

   **Two holes remain, and they are stated here rather than left for a reader
   to discover, because a clause that overstates what ships is the failure
   this whole section is about.** Neither is reachable at human cadence, but
   "not reachable" is a claim about people and should be written as one.
   (a) A correction press arriving within about **60 ms of the release**
   can be dropped — the gate reopens on a *sample*, so a press before the
   sample that observes the release has nothing to reopen it. That is
   inherent to a sample-based gate and no anchor width fixes it. A real
   double tap leaves 100–300 ms and is never affected.
   (b) The **400 ms pre-press hold** samples nothing, so a second press of
   the *wake* button inside it is lost whenever the device was still being
   held at boot. This one is a genuine regression against pre-gate
   behaviour and is M2-T13.
6. **One physical press must latch exactly once.** This is not the truism it
   reads as, and it is recorded because the device got it wrong for the whole
   of M2. The pads are wired to fire on a **falling** edge, and a *release*
   produces one too; the 50 ms debounce is measured from the **press** edge,
   so the release of any normal 100–300 ms hold clears it and was accepted as
   a second press. No fixed window measured from the press can close that,
   because how long someone holds a button is unbounded. The fix is a
   **release gate**: a falling edge counts as a press only once the button has
   been *observed back up* since the last one.

   Two things about it are worth keeping. It was **latent, not new** — the
   phantom edge was always generated, and was harmlessly discarded by a bare
   latch drain until M2-T8 put the ack coalescer above that drain and started
   treating every latched bit as a press. And it is why clause 5 could not be
   built by simply counting presses per button: counting on top of a
   double-latching edge source would have turned an intermittent wrong answer
   into a reliable one, every press toggling twice.

The panel still gets its **ghost-clean skip** on the chore screen: a tick mark
is a tiny diff and the screen is left within seconds, so the ghosting it
prevents has nowhere to accumulate. That is legal — refresh *cadence* is
display.c policy while panel protection is the driver's, and this changes only
the former. The **1 s driver guard is not negotiable** and must not be
"optimised": it is RTC-persistent panel protection, and the invariant names
merging those two layers as the thing not to do.

**Power discipline.** The pixels light only on a **button** wake. An unattended
tick or NTP wake that happens to paint the chore screen leaves them dark —
otherwise chore mode would light four LEDs every 55 seconds for nobody.
`neopixel_stop_sync()` before sleep is mandatory and is already the contract
(`neopixel.c` is the sole RMT and power-gate owner).

**No chirp.** Two chores can legitimately be ticked in one go — "no homework
today, and I just did the dishes" — and that should not make noise twice. The
one-off reward sound for *completing the day's list* is a different thing and
stays deferred (§9).

The transition *out* of chore mode stays a full refresh: the whole screen
changes.

Module home: `chores_led_for(mask, n, released)` — a pure mask → four-RGB table
plus one
painter over `neopixel.c` — sits beside `status_led_for_state()`, which is
already exactly that shape.

### 2.6 The break screen prompts, and stays consistent

During a Screen Break the break screen gains a chore count and the same
A-is-mode row:

```
┌──────────────────────────────────────────────────┐
│               SCREEN BREAK                       │
│  ████████████████████░░░░░░░░░░░░░░░░░░░░░░░░░░  │
│                  12:34                           │
│  Chores 2 of 3                      Screen 1:30  │
│  Chores                  → Piano            ⟳    │
└──────────────────────────────────────────────────┘
```

**Amended after M2-T6/T6a, which measured what the first sketch could only
guess at.** The sketch above originally drew four items on the button row and
a centred `2 chores left` above it; neither survived contact with the panel,
and this section now records what is built.

*The frozen screen time is not on the button row.* At 16 pt `Screen 1:30` is
90 px, and centred over button B it spans x 46..136 — into `Chores` at one end
and the swap hint at the other. Only three items fit that row, so the fourth
moved up to a line of its own, right-aligned. A configured list lifts the bar
and the countdown to open that band; with no list every band sits exactly
where it always did, which is why the two no-chore cells are unchanged to the
byte. Cell B stays empty either way, because the break is still enforced for
the Screen timer and `display_button_b_label()` yields nothing for a break.

*The prompt counts what is **done**, not what is left,* so that the two screens
never show the same-looking figure with opposite meanings — the checklist
itself already reads "n of 3". It is left-aligned and the tick follows the
word: `Chores` is the item whose text changes, and a right-anchored label of
changing width walks its own left edge across the panel on every ack. When the
list is finished the line reads `Chores ✓`, reusing the checklist's own glyph
rather than introducing a box — LVGL's symbol font has no box, and the device's
existing vocabulary is already "tick = done, nothing = not done".

*And it reads "2 of 3" rather than "(2/3)" for a reason worth recording:
height, not width.* Letters and digits paint 12 ink rows on this band; any of
`(`, `)`, `/`, `[`, `]` rises above cap height and falls below the baseline and
paints 17. The panel has 80 rows between the title and the button row, the
three bands need 67, and four 4-row gutters need 16 more — 83 does not fit in
80. A bracketed fraction would have to be paid for by moving the title, for
zero slack.

A break is the natural moment to do chores, so the device says so. That is a
**prompt**; §3 argues at length that it must not be the **gate**. A goes to
Chores, C still swaps to the next timer, and both work because a BREAK is not
RUNNING — the §4.2 reachability rule lets chore mode in during a break, which
is exactly when it is wanted.

The existing suppression rule needs generalising rather than extending. Today
the break screen drops its whole button row when `swap_next_name == NULL` (no
break-eligible timer). That condition is no longer the same question as "is
there a button row", because the row now has independent cells:

| Chores? | Break-eligible timer? | Break-screen row |
| --- | --- | --- |
| yes | yes | full row: A Chores, C swap |
| yes | no | A Chores, no swap hint |
| no | yes | no A, C swap — today's row |
| no | no | no row at all — the centred `Timer paused - 1:30:00 left` footer, exactly as today |

Only the last cell keeps the legacy footer. Three new goldens.

## 3 · The gate

### 3.1 Why "the break isn't over until chores are done" is the wrong primitive

Taking it on its own terms first, because it was the opening ask:

1. **The enforcement point may not exist.** Allocation ≤ break interval ⇒ no
   break ⇒ no gate. A 30 min weekday against the default 30 min interval never
   fires one.
2. **Its value is arbitrary.** The amount held hostage is "whatever screen time
   was left when the break happened" — 30 min on a 60 min day, 5 min on a day
   the kid started late. The same non-compliance costs wildly different amounts
   on different days, which makes it unlearnable.
3. **It fights the eye rest.** The break has an absolute wall end *by design*
   (`break_expiry_wall`, the two-event sleep planner, the ≤75 s chime grace).
   Making the end conditional turns a predictable 15-minute rest into an
   open-ended lockout and makes the rest itself feel like the punishment.
4. **It punishes the wrong thing.** "A break that goes to violin is valid" is
   already true and must stay true.

Point 3 has a structural consequence worth keeping even though the idea is
rejected: if this is ever revisited, **do not implement it by extending the
break.** The break should end normally — chime, snap-back, `break_expiry_wall`
cleared, latch drained — and the gate should be a separate refusal on *resuming
Screen*. That seam already exists: `timer_start_allowed()` returns false for
slot 0 during a break precisely so the start is refused and the ▶ glyph is not
drawn.

### 3.2 The split allocation

> The Screen timer's first `chore_free` minutes are unconditional. The rest of
> the day's allocation is withheld until every chore is acked, and is released
> the moment the last one is.

With a 60 min day and `chore_free: 20`: the kid sits down and gets 20 minutes,
no argument, no negotiation. At 20 minutes the timer expires. Chores done → the
remaining 40 lands and Screen goes PAUSED holding it. Press B.

Against each objection above:

1. **The enforcement point always exists.** Every day has a first Screen start.
   It does not depend on a break firing, on the exposure balance, or on the
   allocation being longer than the break interval.
2. **Its value is fixed and legible.** Exactly `allocation − chore_free` is at
   stake, every day, knowable in advance by everyone in the house.
3. **It leaves the eye rest alone.** Breaks keep their absolute end, their
   chime, their two-event sleep planning.
4. **One knob spans the policy space** — see §3.3.

### 3.3 Per day type, which is what makes one knob enough

`chore_free` is four settings, mirroring the four allocations:

| Day type | Allocation | `chore_free` | Effect |
| --- | --- | --- | --- |
| Weekday | 60 | **0** | Fully gated. Nothing until the chores are done. |
| Weekend | 120 | **30** | Morning cartoons, then chores for the rest. |
| Holiday | 120 | 30 | as weekend |
| Summer | 120 | 60 | a longer leash |

Two boundary readings, stated precisely because they are one character apart:

- `chore_free == allocation` ⇒ nothing is withheld ⇒ **the gate is off for that
  day type.** This is the per-day-type off switch and it needs no extra key.
- `chore_free > allocation` ⇒ **a config error** (§5.3). It cannot mean
  anything, so the device refuses to guess.

`schedule.c` already resolves the day type for the allocation lookup, so
`chore_free_for_day()` is a sibling of a function that exists.

### 3.4 What the gate does **not** touch

- **Extra timers.** Violin, Piano, Meditation and Laundry all start, run and
  expire exactly as today, gated or not. The gate is slot 0's alone.
- **The exposure balance and break scheduling.** Untouched. A gated day still
  earns and serves breaks on exactly today's rules — including a break earned
  entirely by a non-eligible extra while Screen never started.
- **Bed Time and the charge lock.** Both outrank everything and are unchanged.
- **The break's end.** Chime, snap-back and the latch are untouched.

### 3.5 Rejected alternatives

| Alternative | Why not |
| --- | --- |
| **Gate the break's release** | The four objections in §3.1. Not shipping, in any phase. |
| **Deduct tomorrow's time per unacked chore** | **Rejected.** It is not needed once the split allocation exists, and a chore ledger that follows the kid into the next day turns a checklist into a debt collector. If the chores are not getting done, that is a conversation, not a firmware feature. |
| **Gate break-eligible timers** | Punishes violin. No. |
| **A "Chores" extra timer slot** | Already possible today with a non-eligible, non-reloadable timer — and it measures *time spent*, not *done*, which is the whole thing being added. |

## 4 · Behaviour

### 4.1 The bar carries the gate — locked block on the left

Not a header chip, and not a label floating in the empty right-hand end. The
bar drains **rightward**: the fill is anchored at the left and its right edge
walks left as time is spent, so the right-hand end of the bar is where *spent*
time already lives. Putting the locked amount there would overlay two different
meanings on the same pixels.

So the locked amount is a **block held at the left**, and the free tranche
drains to the right of it:

```
     locked (does not move)          free tranche (drains rightward)
   ┌───────────────────────────┐   ┌─────────────────────┐
   │  0/3 Chores · 40 min      │   │███████████░░░░░░░░░░│
   └───────────────────────────┘   └─────────────────────┘
```

Full screen, 60 min day with `chore_free: 20`, ten minutes used:

```
┌──────────────────────────────────────────────────┐
│  Sat May 16  12:34 PM       Last sync: 12:30 PM  │
│  │0/3 Chores · 40 min │████░░░░░░                │
│  ▮85%                       00:10:00             │
│  Weekday · 60 min                     RUNNING    │
│  Chores          ⏸          →          ⟳         │
└──────────────────────────────────────────────────┘
```

- The locked block is `withheld / allocation` of the 280 px, **outlined and
  unfilled**, holding the label. Black text on white is the legible direction on
  this panel; a label over a filled bar would be half-inverted.
- Pixels-per-second stays **uniform across the whole bar** — the free tranche
  occupies `chore_free / allocation` of the width and represents `chore_free`
  seconds — so the bar does not silently change scale at the boundary.
- The locked block **does not move** while the free tranche drains. It is a
  fixed statement about the day, not a second countdown.
- **On release the block simply vanishes** and the bar goes full width with the
  ordinary `remaining / allocation` fill. That jump *is* the feedback, and it is
  why the release does not need the parenthetical (§5.2).
- **Fully gated** (`chore_free == 0`): there is no draining region at all, so
  the bar is just the text — `0/3 Chores to unlock 60 min`.
- No chores, or released: no block, no label, bar exactly as today.

Font: **12 pt**, black-on-white, pending a look at real hardware in phase 2
(§8, Q-A). The inverted break screen is where 12 pt fails; this is the
forgiving direction.

### 4.2 Reachability and mode

**Chore mode is refused while the active slot is RUNNING.** You cannot tick off
"dishes away" while the TV clock ticks. The predicate is not new — it is the
RUNNING half of `timer_swap_allowed()` ("refused while the active slot is
RUNNING"), without that function's second condition that extras must exist.
Since the state model guarantees only the active slot can ever be RUNNING, "no
timer is running" and "the active slot is not RUNNING" are the same test, so the
check is one existing `timer_get_state()` comparison rather than anything new in
the timer module.

It falls out well:

- **BREAK is not RUNNING**, so chore mode is reachable throughout a break —
  exactly where §2.6 wants it.
- A **background break with violin running** blocks it, correctly: the kid is at
  the violin.
- Button A is therefore not worth a wake while RUNNING, which is precisely the
  `buttons_policy_wake_mask()` idiom — a press that could only be refused must
  not burn a wake and a panel refresh.
- And the release can now **never** land on a RUNNING timer, which deletes the
  hardest case from §5.2.

**Mode is a render selector, never a control-flow branch.** Every wake does all
of its ordinary timer work — day rollover, the bedtime gate, `timer_tick`, the
break-end drain, the network window — regardless of which mode is showing; only
the *paint* differs. This is written down because the tempting implementation is
an early return into a chore-screen handler, and the break-end latch has already
been stranded once in this codebase by exactly that shape of mistake.

**Reverts are deliberately minimal**, so the device is never fighting the user:

- **Day rollover** reverts to Timers. Approved and the only automatic revert.
- **The final ack does NOT revert.** Bouncing out of chore mode on the last ✓
  would mean a mis-press costs a trip back through the mode button to undo. The
  screen says `Screen time unlocked` (§2.4) and waits for A.
- A **tick or NTP-sync wake landing on the chore screen is fine** and repaints
  it, exactly as it would repaint the timer screen.
- **Break end** is the one proposed exception: it already forces a full refresh
  and snaps the selection back, so it reverts to Timers too — the kid did not
  press anything, and the whole point of that repaint is to show the new
  situation.
- If chore mode is stored but **no chores are configured** (the list was
  emptied), the mode reverts to Timers. A guard at the paint-time choke point
  (`make_display_state`), and it **stores** as well as renders. *(Amended in
  M2-T2; this bullet first said render-only.)* Render-only is not enough
  because `timer_mode()` is the byte Button A reads: a fallback that fixed
  only the paint would leave the stored mode saying Chores while the panel
  says Timers, and the first press of A would toggle from the stale value
  straight back to Timers — a button that visibly does nothing.
  **The cost, stated rather than left to be found:** `chore_store_load_names`
  zeroes the count before anything can fail and returns non-`ESP_OK` on *every*
  failure — a failed NVS open, a blob-version mismatch, a count above
  `CHORE_MAX` — and the app-state read discards that return code. So the guard
  cannot tell "the list is empty" from "the list is unreadable", and because it
  stores, one transient NVS read error on one paint permanently overwrites a
  mode the user set. The render-only fallback would have self-healed on the
  next good read; the stored revert cannot. Accepted: the impact is one extra
  press of A, and the alternative is the dead button above.

### 4.3 Behaviour rules (the TDD contract)

| # | Situation | Behaviour |
| --- | --- | --- |
| C1 | No chores configured | Feature entirely inert. No mode button, no bar block, no gate, no pixels. **The default; existing devices see no change beyond the remap.** |
| C2 | Chores configured, none acked, Screen IDLE | `timer_start` allocates `min(allocation, chore_free)`. The withheld remainder is derived, not stored (§5.2). |
| C3 | Any attempt to reach chore mode while a timer is RUNNING | **Refused** (§4.2). Button A draws no label. The first draft's "acked while RUNNING" rows are unreachable by construction. |
| C4 | Last chore acked while Screen EXPIRED | Remainder released; slot goes PAUSED holding it. Press B. |
| C5 | Last chore acked while Screen IDLE (never started today) | Remainder released; the day's first start is now the full allocation. **No timer call needed** — the allocation is read live. |
| C6 | Last chore acked while Screen PAUSED | Remainder added to `remaining_at_pause`. |
| C7 | Last chore acked during a BREAK | Release applies to slot 0's frozen `remaining_at_pause`. The break's end is **not** moved. |
| C8 | A chore toggled back off after release | **Stays released today.** Release is a latched day flag, not a recomputation. Nothing is clawed back — and nothing is gained by the toggle, so there is nothing to game. |
| C9 | A chore toggled off *before* release | Gate re-arms normally; it was never released. |
| C10 | Chore list edited (hash mismatch) | Acks cleared, **release flag preserved** — a list edit must not re-lock a day that already released (C8). |
| C11 | `chore_free > allocation` for **today's** day type | The config-error screen engages (§5.3). |
| C12 | `chore_free > allocation` for a day type that is **not** today | Named in the `config_ack`; dormant. The device does not block in December over a broken summer setting. |
| C13 | Day rollover | Acks cleared, release flag cleared, mode reverts to Timers, gate re-arms. Same edge as `timer_reset`. |
| C14 | Power cycle / panic / OTA reboot | Acks survive (§5.1). A kid must never redo a chore because the firmware updated. |
| C15 | Bed Time or charge lock engages while gated | Locks win, as always. Unchanged. |
| C16 | Chore mode active when the device sleeps | Persists. Only a day rollover, a break end, or an emptied list takes it back to Timers (§4.2). |
| C17 | Unattended wake paints the chore screen | Panel repaints; **pixels stay dark** (§2.5 power discipline). |

### 4.4 The trust model, stated on purpose

A kid can press ✓ on "Dishes away" without touching a dish. This is the same
trust the Screen timer and the Violin timer already assume, and the
break-eligible plan settled it once already: *"That is unfixable in principle —
the device cannot see the room… Do not harden it."* The same applies here, and
it is the reason §1.4 makes HA read-only rather than building an override race,
and the reason chore debt (§3.5) is rejected rather than deferred. The device is
a **ritual and a record**, not an enforcer.

## 5 · State, and the two traps

### 5.1 Where acks live

RTC memory alone is **wrong**. `RTC_DATA_ATTR` survives deep sleep only; an OTA
reboot or a panic zeroes it, and C14 says a firmware update must not cost the
kid their chores. Follow `timer_persist.c`'s pattern:

- **RTC** (`rtc_state_t`): `uint8_t chore_acked` (3 bits used), a
  `chore_released` flag, and the current mode (C16). Bumps `RTC_STATE_VERSION`.
- **NVS** (`chore_ack`, its own key):
  `{ char date[11]; uint16_t list_hash; uint8_t acked; uint8_t released; }`,
  written on every toggle and restored when the date is today. Toggles are a
  handful of writes a day, so this needs none of the "write only when the blob
  changed" flash-wear care `timer_persist` takes.

Names live in their own NVS blob (`chores`), written by `config_apply`,
version-stamped and length-checked like `nvs_timer_defs_blob_t`.

Ack bits are **positional**, so the stored `list_hash` over the names is what
keeps them honest: a mismatch clears `acked` and preserves `released` (C10). At
three chores, re-acking after an edit costs three presses.

### 5.2 Trap one — the release must not be an adjustment

The obvious implementation is `timer_adjust(0, +withheld)`. It is wrong, and
the reason is recent: `adjust_today_sec` is the truthful record of *what was
asked for* and drives the panel's `(-30 min today)` parenthetical (`3110eaa`).
That parenthetical is reserved for the screen-adjust field. A gate writing +40
into it would manufacture an adjustment nobody made — verbatim the bug that
field was introduced to fix.

To be clear about what "invisible" means here: the release is **not hidden from
the user**. The locked block vanishing and the bar going full width (§4.1) is
loud, immediate feedback. What it must not do is claim to be a *screen
adjustment*, because that line has one meaning and a second writer would ruin it.

So the release needs `timer_adjust`'s **state machine** without its
**bookkeeping**. Do not duplicate the former to avoid the latter. Split it:

```c
static bool adjust_core(int slot, int32_t sec, bool record);

bool timer_adjust(int slot, int32_t sec) { return adjust_core(slot, sec, true); }
bool timer_release_gated(int32_t sec)    { return adjust_core(0, sec, false); }
```

One state machine, two bookkeeping policies, and `test_timer` gets a row
asserting the release moves `remaining` and leaves `adjust_today_sec` alone.

The withheld amount itself is **derived, not stored**:

```
withheld = released ? 0 : max(0, allocation_for_day − chore_free_for_day)
```

computed at the point of use with the allocation read live, as it already is.
Nothing new to keep in sync. And §4.2 means the RUNNING case never arises, so
`adjust_core` is only ever entered from PAUSED / EXPIRED / BREAK — states whose
contracts `timer_adjust` already documents — plus the IDLE case that needs no
call at all (C5).

### 5.3 Trap two — a bad `chore_free` blocks the device

`chore_free > allocation` cannot mean anything. Validating it at write time is
necessary but **not sufficient**: the two are independent settings, so a valid
pair goes invalid the moment someone edits `weekday_min` down without touching
`chore_free_wd`. Cross-field validation on the document catches one direction;
nothing catches the later single-field edit.

Three layers, and the last one is deliberately loud:

1. **The `chore_free_*` setter rejects** a value above its paired allocation,
   named in the `config_ack` `errors` list.
2. **The allocation setter clamps** the paired `chore_free_*` down to match, and
   says so in the ack. Rejecting here would be wrong — a parent lowering screen
   time should not be blocked by a chore setting they are not thinking about.
   Each direction does the kind thing, which makes the invalid state unreachable
   by ordinary operation.
3. **A blocking config-error screen**, for when it happens anyway — a config
   written by an older firmware, an NVS oddity, a bug in either setter.

Layer 3 is the decisive one and it is deliberately not subtle. An `errors` entry
in a `config_ack` is read by nobody. A kid arriving with the device saying *you
broke it* is an alert that cannot be ignored, and it routes the problem to the
person who can fix it in about ten seconds.

Shape it on the **Bed Time lock**, which is the existing precedent for "paint
one screen, then sleep in long intervals that still run a network window so the
fix can arrive and the gate can re-check":

- Engages only when **today's** day type is the broken pair (C11/C12). The
  device does not block in December over a broken summer setting.
- Names the offending pair on screen, so the fix is obvious without a laptop.
- Sleeps charge-lock style, but **keeps Button D as a wake source** so a parent
  can force the corrected config in immediately rather than waiting out an
  interval. This is the one place it should differ from the bedtime lock, which
  drops every button.
- Re-checks every wake and releases when the pair validates, with
  `lock_gate_promote_render()` promoting that wake's partial to a full refresh —
  which already exists for exactly this.

The `chore_free_for_day()` clamp stays as a belt regardless, so no code path can
hand `timer_start` a negative allocation even if the gate is somehow bypassed.

This makes a **third** thing that can lock the device, which is worth naming as
a cost rather than discovering later. It is bounded: the bad pair can only get
there through a channel that was working at the time, and D keeps the fix one
press away.

## 7 · The HA dashboard (in scope)

The settings count has outgrown the auto-generated MQTT device page — four
allocations, four `chore_free`, quiet hours, bed time, two break settings, four
timer slots × four fields, three tone selects, volume, timezone, name, two OTA
fields. Configuring a device from that card is already tedious and this feature
makes it worse. So the feature ships its own dashboard.

**This is only viable because entity IDs are stable.** `def_ent_id` makes them
MAC-derived rather than name-derived (`docs/home_assistant.md`), so a shipped
YAML needs exactly one substitution — the device id — and does not break when
someone renames the device. Requires HA 2025.10+, and an already-paired device
needs the one-time re-registration already documented there.

Two views:

- **Config** — grouped sections with headers (Allocations · Chores · Breaks ·
  Quiet hours & bed time · Timers 1–4 · Alerts · System & OTA), so related
  numbers sit together instead of alphabetically. Pairing each allocation with
  its `chore_free` in the same row is the layout that makes the §5.3 rule
  obvious without reading anything.
- **Report** — screen minutes per day and chore completion as statistics
  graphs, per-timer runs, battery and exposure-balance history, OTA state. This
  is the view that makes the recorder history (§1.4) actually visible.

Shipped as `tools/ha_dashboard.yaml.tmpl` plus a small generator that
substitutes the device id, in keeping with the existing `tools/` scripts, and
documented in `docs/home_assistant.md`.

## 8 · Open — hardware checks, not decisions

Every design fork is settled. Two things want a real panel in front of them
during phase 2:

- **Q-A — 12 pt in the locked block** (§4.1). Expected to be fine
  black-on-white; the size only fails on the inverted break screen. Confirm on
  hardware before the golden is fixed, since regenerating a golden for a font
  change afterwards is indistinguishable from regenerating it to hide a bug.

  **ANSWERED 2026-09-22 — as expected.** Legible black-on-white on the panel;
  the four `main_chore_gated*` goldens are final. The prediction that the size
  only fails inverted still stands and is untouched by this.
- **Q-B — NeoPixel ↔ button ordering** (§2.5). The mapping is chores 1–3 → three
  pixels, gate → the fourth. Whether the physical pixel order runs the same
  direction as the physical button order is a look-at-the-board question, and
  getting it backwards would make the feedback actively misleading.

  **ANSWERED 2026-09-22 — it runs backwards.** `k_chore_pixel` inverts to
  `{2,1,0,3}`. Worth keeping the reason this was asked rather than assumed:
  nothing on the host side could have caught it, because both orderings are
  internally consistent and every test passes either way. The gate pixel is
  the fourth entry of the same table and inverts with the rest.

**A third thing emerged that this section did not anticipate**, and it is the
shape to expect from future board time — not a design fork, but a figure that
only a person pressing buttons can settle:

- **Q-C — the ack hold** (§2.5). `CONFIG_MAGTAG_STATUS_LED_ACK_HOLD_MS`
  shipped at 250 and **250 is too short**: a person cannot reach each chore
  before the refresh starts. Raised to 400 on 2026-09-22. That is a first
  correction from one session, not a swept value — it wants another pass, and
  it is a build-time Kconfig knob precisely so sweeping it is cheap.
- **Q-D — the ack burst budget** (§2.5), `CONFIG_MAGTAG_CHORE_ACK_BURST_MS`,
  added 2026-09-23 at **4000** and **also unswept**. It replaced a bound of
  three *windows* — one per chore row — which turned out to be the wrong
  shape once a mis-press could be corrected: a full list used every window
  ticking it, leaving none to undo with. The loop now runs two clocks, an
  idle window that resets on each press ("is the person still pressing?") and
  this budget, which never resets ("is this still a person?"). The budget's
  job is the flaky-pad bound — a pad generating edges must not be able to
  hold a battery device awake — so it must stay finite whatever a board says
  about comfort. Sweep it with Q-C: they interact, since the budget is worth
  about ten idle windows at the current hold.

  Both knobs are unswept, and that is now two figures resting on one
  session's impression. **If a second board session happens, sweep these
  together and record what it finds here**, because "400 and 4000 felt right
  once" is the whole of the evidence behind the pair.

**A note on reading absences as defects.** The same session reported "no chime
when all chores were completed". That is §2.5 working as specified ("No sound")
plus §9's deferred reward sound, not a bug — but it was reported as one by the
person who wrote both sections, which is a fair warning that a deliberate
silence is indistinguishable from a broken feature at the panel. See §9, where
the decision and its quiet-hours behaviour are now recorded.

## 9 · Deferred

- Per-day-type chore *lists* (weekday vs weekend chores). The day-type machinery
  now exists for `chore_free`, so this is a smaller step than it was.
- More than three chores. If it ever goes past ~8 the list wants its own
  retained topic rather than a bigger `CONFIG_BUF_MAX`. Note that the current
  design spends one NeoPixel per chore, so the pixel feedback does not scale
  past four and would need rethinking first.
- Chore **streaks** and a weekly rollup in the daily summary payload — a good
  fit for the reporting view in §7 rather than the panel.
- A **reward sound** when the last chore lands — the one-off, not a per-ack
  chirp (which §2.5 rejects). `tones.c` already synthesizes note tables, so a
  rising arpeggio in the spirit of a 1-up is a few lines and no assets. A
  literal sampled one is Nintendo's, so if you want that exact sound it goes on
  the assets partition as your own WAV via the existing Custom WAV path rather
  than shipped in the repo.

  **Raised again from the board on 2026-09-22** ("there was no chime alert for
  when all chores were completed") and **confirmed deferred** — recorded here
  because its absence reads as a defect to anyone testing the feature, and it
  is not one. Two things are settled for whoever picks it up, so neither gets
  re-litigated:

  - **It rides the existing fixed-chirp path**, not the tone registry.
    `audio_break_over_chime()` is the model: a short fixed fire-and-forget
    chirp with no NVS tone selection, no HA entity and no `alert_kind_t`
    of its own. That is what keeps it "a few lines".
  - **It plays through quiet hours** (user decision, 2026-09-22), consistent
    with letting the NeoPixel ack through the mute. This makes it the only
    audio on the device that ignores quiet hours — deliberate, and worth a
    comment at the call site so it is not "fixed" later as an oversight.
    Revisit only if a chore acked late at night turns out to carry further
    than expected; the LED precedent does not settle the audible case.
