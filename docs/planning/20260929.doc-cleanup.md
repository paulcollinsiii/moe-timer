## Goal

Every doc in `docs/` is for a **human reader**. Each one has one stated purpose
in its first paragraph, and nothing in it strays from that purpose. Content that
only serves a coding agent moves to `docs/agent_notes/<subsection>.md`. History
belongs in git and gets deleted from the docs. Deep "why this module does X"
detail belongs in code comments next to X.

**This is a rewrite, not a reshuffle.** Approach it as an author who has the
precision of an engineer:
- **The author's side** is editing, clarity, focus and flow. A doc reads start to
  finish as one argument, puts each point where the reader needs it, and cuts
  whatever doesn't serve the reader.
- **The engineer's side** is precision, correctness and detail. What stays is
  exactly right, verified against source, and specific enough to act on.

Heavy edits to every section are expected. The point each section makes must
survive, but its prose does not need to. If the ~245 KB of human docs today is
only split into more files, the cleanup has failed. Size alone will not
measure this: the test is whether the result is approachable, organized and
concise to a human reader. That takes an editor's judgment, which is why the
review cycle is built around a reader (see [Review cycle](#review-cycle-per-stream-after-phase-2-and-again-after-phase-3)).

This is a documentation-only change. The only non-doc edits allowed are:
- `test/test_gen_ha_dashboard/`'s doc-reading assertions (see [Tests that read docs](#tests-that-read-docs));
- doc paths quoted in source comments (link retargeting only);
- comment blocks that receive "deep detail" moved out of a doc (comment text only, no code);
- `.claude/CLAUDE.md` (section rename + doc pointers, Phase 3). The file is
  gitignored, so this is delivered as a patch for the owner to apply;
- `include/credentials.local.h.example`: its two "erase NVS" comments (Phase 0 D4.1). **Done** in Phase 1 (a094f8e), so the template and README agree;
- stale comments listed in Phase 0 D4.3, including one in-place edit to `main/main.c` L522

## Ground rules for every phase

1. **Move, don't lose, and condense.** Before a section leaves a doc, it gets
   exactly one destination in the [content map](#content-map). Allowed
   destinations: another human doc, `agent_notes/`, a code comment, or *delete*
   with a reason ("history, in git", or "duplicate of X"). What lands at the
   destination is rewritten to the size its point needs, not carried over
   verbatim.
2. **One fact, one home** (memory: *one-fact-recorded-at-n-sites*). When a fact
   appears in several docs, pick an owner doc and have the others link to it.
   `ProductOverview.md` and `architecture.md` currently both carry a hardware
   table and a module table. Architecture owns both.
3. **Architecture is not behavior.** Architecture covers what the parts are,
   how they are layered, what state lives where, and the invariants. Behavior
   covers what the device does when a kid presses B. Operations covers how you
   set it up, run it and debug it.
4. **Each doc does its one job and nothing else.** Don't add adjacent material
   because it has nowhere else to go. Examples: testing guidance does not
   belong in `developer_setup.md`, and HA mechanics do not belong in behavior
   docs. If something has no home, list it here as an open item.
5. **Verify against source, not against the old prose.** Where a doc makes a
   claim about code (function names, orderings, counts), check it in the tree
   before carrying it forward. The layer-direction section of architecture.md
   already records three consecutive commits that got this wrong.
6. **Code-comment moves:** comment text only. `.c`/`.h` must still pass
   `clang-format --dry-run --Werror`. **Add no lines to `main/main.c`**, not even
   comments; its adversarial-review rule counts lines. Deep detail about main.c
   goes to the called module's comment or to `agent_notes/`.
7. Edit files with the Edit/Write tools, not scripted text edits (memory:
   *edit-files-with-tools-not-python*). Every subagent brief repeats this.
8. `ota_manifest.md` is a good example of a focused doc: one subject, what you
   need to use it, and the pitfalls. It shows the intent, not a template to copy.

## Invariants: two different lists

These two lists are not the same kind of rule, so they live in different places.

- **System invariants** hold for the running device, and are true at every
  instant. Examples: "zero or one timer slot is ever RUNNING"; "BREAK lives
  on slot 0 only"; "GPIO 21 is HIGH before any other peripheral code runs";
  "`ntp_sync()` never changes `expiry_wall_time`"; "the app slot size never
  changes after the first OTA-capable flash". They go in the top-level
  `architecture.md` as a table (invariant, why, where enforced/tested), fully
  spelled out rather than referenced.
- **Development rules** are rules for whoever changes the code. Examples:
  pure C, IDF 6 component names in `REQUIRES`, golden files are regenerated
  only for intentional layout changes, `timer_defs_install()` runs before any
  `timer_*` call. They stay in `.claude/CLAUDE.md`, and its `## Invariants`
  heading is renamed **`## Development rules`**. Entries that are really system
  invariants (the NeoPixel gate, the `ntp_sync` rule) are moved to
  architecture.md and replaced there by a single link.

Phase 0 produces both lists, and the owner signs them off.

### Review cycle (per stream, after Phase 2 and again after Phase 3)

Implementor, then an adversarial reviewer, then a separate fix agent (memory:
*start-work-means-implementor-reviewer-cycle*).

The reviewer works in two passes that mirror the two sides of the goal. Most
of this is judgment rather than something a script can check, so findings are
written as an editor's notes: name the passage, say what is wrong for the
reader, and propose the fix.

**Editor's pass (read as the doc's reader, start to finish, before checking anything):**
1. **Brief:** can the reader answer each question in the doc's Phase 0 brief
   from this doc alone, following links only when they choose to go deeper?
   Having to open a second doc to understand the first is data at a distance,
   and it is a finding.
2. **Focus:** does the first paragraph state the purpose, and does every
   section serve it (ground rule 4)? Agent-only material, history, and "why
   the code does X" digressions are findings.
3. **Flow:** does the doc build in the order the reader needs it? Does each
   section lead with its point? Do transitions carry the reader, or does the
   doc read as a list of facts?
4. **Economy:** a passage carried over close to verbatim, or a paragraph
   that restates its neighbor, is a finding even when it is accurate. Size is
   a signal to look closer, never a verdict.
5. **Fit:** would a doc read better merged into a sibling (e.g. a short
   `screen_breaks.md`) or split?

**Engineer's pass (check against the tree):**
6. **Nothing lost:** every content-map row's *point* is present at its
   destination, or its deletion reason holds.
7. **Correctness:** every claim that names code, a value, an order or a
   limit is checked against source (ground rule 5). Precision lost in the
   condensing ("wakes about once a minute" where the planner naps 5–64 s to
   land on the minute boundary) is a finding.

A stream is done when a second editor's pass comes back with no structural
findings (brief, focus, flow, fit), not when the checklist is merely ticked.
