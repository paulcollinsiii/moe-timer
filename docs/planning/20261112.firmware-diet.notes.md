### 2. `CONFIG_ESP_ERR_TO_NAME_LOOKUP=n` — ACCEPTED (costs log readability)

- Call sites: 53 lines in `main/`, `components/`, `include/` mention
  `esp_err_to_name` (3 more in managed_components); every one is an argument
  to an `ESP_LOGx`. None is published over MQTT, stored in NVS or compared
  (grep). `docs/` and `tools/` quote no `ESP_ERR_*` name that a log line
  would have to produce. IDF itself also calls it (`ESP_ERROR_CHECK`,
  cpu_start).
- What the logs lose: `esp_err_to_name_r` falls back to `strerror_r`, then
  to `"UNKNOWN ERROR 0x<hex>(<dec>)"`. So `(ESP_ERR_NVS_NOT_FOUND)` in a log
  line becomes the numeric code and has to be decoded from `esp_err.h`.
  Codes are still unambiguous. The owner may prefer the 7.8 KB; this is the
  one accepted item that costs debuggability, so it is its own commit and
  reverts alone.
- Map: `esp_err_msg_table` (0x6b8 B) and its message strings gone.
- Size: 1,508,752 -> 1,500,976 B (-7,776 B); 81.8 % of slot. 0 warnings.
- sdkconfig diff: exactly one symbol, `CONFIG_ESP_ERR_TO_NAME_LOOKUP`
  (was `y` under `# default:`, now `# CONFIG_..._LOOKUP is not set`); no
  other line changed.
- Host tests: no host-compiled code involved (host builds stub esp_err);
  see final 54/54 run recorded in the 3rd entry.
- Other checkout: `idf.py reconfigure` (line was `# default:`); otherwise
  menuconfig, Component config, Common ESP-related.
- Bench check: provoke any logged error (e.g. wrong MQTT URL) and confirm the

### 4. scanf family — DROPPED

- Who pulls it in (map cross-reference, picolibc `libc.a`): `sscanf` is
  referenced only by `libmain.a(cJSON.c.obj)`; `vfscanf` only by `sscanf`;
  `atof_ryu` only by `vfscanf`. Our own code has no `scanf` call
  (`grep sscanf main components include` is empty). The single call is
  vendored `lib/cJSON/cJSON.c:626`, `print_number()`'s
  "does `%1.15g` round-trip" check.
- Size at stake, from the map: `vfscanf` 2,900 + `atof_ryu` 315 + `sscanf`
  and `ungetc` (about 130) = about 3.3 KB (0.18 % of the slot). `strtod`
  stays (cJSON parse).
- Why dropped: the caller is not ours, it is vendored cJSON 1.7.19. The only
  removal is a local patch of upstream code (replace the `sscanf` with
  `strtod`), forking `lib/cJSON` for 3.3 KB; the failure mode is a number
  printed with different digits in an HA document. Not "ours and trivially
  replaceable", saves next to nothing. Revisit only if a cJSON upgrade is
  already happening (stream F).

## Wake latency items

### W1. `CONFIG_SPIRAM_MEMTEST=n` — ACCEPTED (latency item; size effect nil)

- Source: `esp_system/port/cpu_start.c:732-740` calls `esp_psram_extram_test()`
  under `CONFIG_SPIRAM_MEMTEST`, i.e. on every boot including every
  deep-sleep wake. `esp_psram.c:s_test_psram` writes one word per 32 B line
  over the full 2 MB, then reads it all back, through the cache at 40 MHz
  (`CONFIG_SPIRAM_SPEED_40M`). IDF's comment above it: "Takes about a second
  to complete for 4MiB". Scaled, roughly 0.5 s for this 2 MB part. THIS IS AN
  ESTIMATE FROM THAT COMMENT, NOT A MEASUREMENT OF THIS DEVICE. If it is
  right it is by far the largest single item between reset and `app_main`.
- Size: 1,484,608 -> 1,484,176 B (-432 B); not the point.
- sdkconfig diff: exactly `CONFIG_SPIRAM_MEMTEST` (`y` under `# default:` ->
  not set). Nothing else.
- What is given up: a faulty PSRAM no longer aborts the boot (`cpu_start`
  would have `abort()`ed with "SPI SRAM memory test fail").
- Does anything use PSRAM? See "PSRAM: report" below. Nothing in `main/`
  asks for it.
- Other checkout: `idf.py reconfigure` (line was `# default:`), else menuconfig,
  Component config, ESP PSRAM.
- Bench: time it. The first app log line's `(ms)` stamp is a time since CPU
  reset: `esp_log_timestamp()` (`components/log/src/os/log_timestamp.c`)
  seeds its base from `esp_log_early_timestamp()` = CPU cycle counter / MHz,
  and the cycle counter restarts at reset, so the stamp includes ROM,
  bootloader and this test (the CPU-frequency value used for the division
  changes during boot, so read it as approximate). Compare the first
  app-task line of a build before and after this commit, over a real
  deep-sleep wake (the bench monitor reattaches after USB re-enumerates, so
  you may only see later wakes; that is fine, the stamp is per boot).
  Note the early `ESP_EARLY_LOG` line "SPI SRAM memory test OK" never shows:
  `ETS_PRINTF` is off, see `sdkconfig.defaults`. Also check every wake still
  works.
