### 4. scanf family — DROPPED

- Who pulls it in (map cross-reference, picolibc `libc.a`): `sscanf` is
  referenced only by `libmain.a(cJSON.c.obj)`; `vfscanf` only by `sscanf`;
  `atof_ryu` only by `vfscanf`. Our own code has no `scanf` call
  (`grep sscanf main components include` is empty). The single call is

  "does `%1.15g` round-trip" check.
- Size at stake, from the map: `vfscanf` 2,900 + `atof_ryu` 315 + `sscanf`
  and `ungetc` (about 130) = about 3.3 KB (0.18 % of the slot). `strtod`
  stays (cJSON parse).

  removal is a local patch of upstream code (replace the `sscanf` with
  `strtod`), forking `lib/cJSON` for 3.3 KB; the failure mode is a number
  printed with different digits in an HA document. Not "ours and trivially
  replaceable", saves next to nothing. Revisit only if a cJSON upgrade is
  already happening (stream F).

## Wake latency items

### W1. `CONFIG_SPIRAM_MEMTEST=n` — ACCEPTED (latency item; size effect nil)

- Source: `esp_system/port/cpu_start.c:732-740` calls `esp_psram_extram_test()`
  under `CONFIG_SPIRAM_MEMTEST`, i.e. on every boot including every
  deep-sleep wake. `esp_psram.c:s_test_psram` writes one word per 32 B line
  over the full 2 MB, then reads it all back, through the cache at 40 MHz
  (`CONFIG_SPIRAM_SPEED_40M`). IDF's comment above it: "Takes about a second
  to complete for 4MiB". Scaled, roughly 0.5 s for this 2 MB part. THIS IS AN
  ESTIMATE FROM THAT COMMENT, NOT A MEASUREMENT OF THIS DEVICE. If it is
  right it is by far the largest single item between reset and `app_main`.
- Size: 1,484,608 -> 1,484,176 B (-432 B); not the point.
- sdkconfig diff: exactly `CONFIG_SPIRAM_MEMTEST` (`y` under `# default:` ->
  not set). Nothing else.
- What is given up: a faulty PSRAM no longer aborts the boot (`cpu_start`
  would have `abort()`ed with "SPI SRAM memory test fail").
- Does anything use PSRAM? See "PSRAM: report" below. Nothing in `main/`
  asks for it.
- Other checkout: `idf.py reconfigure` (line was `# default:`), else menuconfig,
  Component config, ESP PSRAM.
- Bench: time it. The first app log line's `(ms)` stamp is a time since CPU
  reset: `esp_log_timestamp()` (`components/log/src/os/log_timestamp.c`)
  seeds its base from `esp_log_early_timestamp()` = CPU cycle counter / MHz,
  and the cycle counter restarts at reset, so the stamp includes ROM,
  bootloader and this test (the CPU-frequency value used for the division
  changes during boot, so read it as approximate). Compare the first
  app-task line of a build before and after this commit, over a real
  deep-sleep wake (the bench monitor reattaches after USB re-enumerates, so
  you may only see later wakes; that is fine, the stamp is per boot).
  Note the early `ESP_EARLY_LOG` line "SPI SRAM memory test OK" never shows:
  `ETS_PRINTF` is off, see `sdkconfig.defaults`. Also check every wake still
  works.

### W2. `BOOTLOADER_LOG_LEVEL` INFO to WARN/NONE — DROPPED

- Evidence on cost: bootloader output goes through the ROM USB CDC putc
  (`bootloader_console.c`, `CONFIG_ESP_CONSOLE_USB_CDC`), whose write is one
  non-blocking `cdc_acm_fifo_fill` per line ("return value ignored — if
  bootloader fails to log something, proceed anyway",
  `bootloader_console_loader.c`). There is no baud-rate wait as on a UART, so
  a line costs the formatting plus a FIFO copy: a few ms for the whole
  ~25-line INFO run at most, an estimate not a measurement. The plan's
  "blocking UART text" premise does not apply to this board.
- `bootloader_console_init()` (USB descriptor patch, PHY pad enable) and
  `usb_dc_prepare_persist()` at hand-off run regardless of the level; the
  level changes nothing about them.
- What is lost at WARN: the "Loaded app from partition at offset" line and
  the segment map, which are the only bootloader record of which slot a
  rollback chose. The bootloader is also not OTA-updatable, so the change
  needs a cable reflash of the bootloader on every device. Small, unmeasured
  saving; real diagnostic loss; extra flashing step. Dropped.
- If a later measurement shows bootloader printing matters, the symbol is
  `CONFIG_BOOTLOADER_LOG_LEVEL_WARN`; remember the bootloader image grows
  only 22,720 of 28,672 B, so nothing else is at stake.

### W3. `BOOT_ROM_LOG_ALWAYS_OFF` — DROPPED (irreversible)

- `components/esp_rom/Kconfig.projbuild`: "The rom log behavior can only be
  changed for once, specific eFuse bit(s) will be burned at app boot stage."
  That is a permanent change to the chip, outside the "efuse-free" condition
  the plan put on it, and the ROM log goes to UART0 and the board has no
  UART bridge (console is USB CDC), so it is not seen on the monitor anyway.
  Not touched.

### W4. PSRAM: report (nothing removed)

- What uses it: the build has `SPIRAM_USE_MALLOC=y`, `ALWAYSINTERNAL=16384`,
  `RESERVE_INTERNAL=32768`, TRY_ALLOCATE_WIFI_LWIP off, BSS/NOINIT in external
  RAM off, `MBEDTLS_INTERNAL_MEM_ALLOC`. `grep` of `main/`, `components/`,
  `include/` finds no `MALLOC_CAP_SPIRAM` and no `psram` reference except
  prose. So the only possible user is a plain `malloc()`/`calloc()` of MORE
  than 16 KB (LVGL's 4,744 B draw buffer is a static in .bss; the OTA and TLS
  buffers are allocated by esp-tls/mbedTLS internal-only). I did not prove
  that no such allocation exists at run time; a heap trace on the bench is
  the proof (`esp_get_free_heap_size()` vs `heap_caps_get_free_size(MALLOC_CAP_INTERNAL)`
  logged after a full network window and an OTA attempt).
- Why not remove PSRAM: the code is written so a PSRAM-less board works
  (`SPIRAM_IGNORE_NOTFOUND=y`, Kconfig help for the OTA heap floor), and the
  2 MB pool is the headroom that makes a 16 KB TLS record plus WiFi fit on a
  PSRAM board. With `CONFIG_SPIRAM=n` the heap shrinks and every figure
  derived on a PSRAM board (OTA min-heap floor, the mqtt_ha budget notes) is
  invalidated. Not overwhelming evidence; not removed.
- What PSRAM costs per wake with the test off: `esp_psram_init()` still
  configures the SPI RAM (CS/CLK pins 26/30, ID read, cache mapping, heap
  region add): in the order of 10 ms, unmeasured. Plus the sleep-entry
  `ESP_SLEEP_PSRAM_LEAKAGE_WORKAROUND` work. Skipping PSRAM init on a deep
  sleep wake is not something IDF offers (it is part of cpu_start), so that
  option does not exist without removing PSRAM.

### Wake path, in order (reset to buttons armed), with what to measure

Config here: ESP32-S2 at 160 MHz, flash DIO 80 MHz, 4 MB, image
validation on every wake (decision 6), USB CDC console, no PSRAM test now.

| Step | What happens | Likely cost (estimate only) | How the owner can measure |
|------|--------------|-----------------------------|----------------------------|
| 0 | EXT1 wake, ROM first stage: reset, ROM banner (UART0, invisible here), load 2nd stage bootloader from flash | a few ms to ~20 ms | wake pad edge on a scope/logic analyser as t0 |
| 1 | Bootloader: console init, read partition table, otadata, pick slot; INFO lines (~25, USB, non-blocking) | ~10 ms | scope t0 to first activity; or bootloader timestamps if the host happens to be attached |
| 2 | Bootloader image validation: reads the WHOLE app image (1.48 MB, dio/80 MHz) through the cache and checks the appended SHA-256 (hardware SHA), then loads IRAM/DRAM segments (about 98 KB IRAM + 18 KB DRAM data copied) | probably the largest bootloader item: tens to a couple of hundred ms, and it scales with image size. Raw flash read alone at dio/80 MHz is ~20 MB/s, about 75 ms for 1.5 MB | scales with image size: compare t0 to the next stage between this branch's builds (1,541,584 -> 1,484,176 B so far); no firmware change needed |
| 3 | cpu_start: clocks, heap, PSRAM init + (was) memtest of 2 MB | memtest, estimated ~0.5 s from IDF's own "about a second for 4 MiB"; now gone. Remaining init ~10-30 ms | the first app log stamp is ms since reset (see W1); compare builds before/after the W1 commit |
| 4 | `app_main` start: `panic_diag_init`, `neopixel_init`, `arm_awake_failsafe`, post-panic quiet (2 s, only after a panic) | under 5 ms normally | `panic_diag` phase marks (BOOT*), or a spare GPIO toggled here |
| 5 | NVS init + defaults fingerprint (flash reads, can erase after a panic), `panic_diag_commit`, TZ, timer guard/defs install/restore (NVS reads) | NVS init ~10-30 ms; the rest a few ms each | `BOOT_NVS`/`BOOT_TMR` marks; add temporary `esp_timer_get_time()` log lines in a local, uncommitted patch |
| 6 | `ota_flow_init` (NVS read), then `buttons_init()`: GPIO config, **`buttons_watch_begin()` installs the ISR service and arms the four button ISRs, seeds the latch with the wake button** | a few ms | this is the point the owner means by "buttons armed": `main.c:590`. A press before it is only the wake press itself, consumed later by `buttons_get_wakeup_button` |
| 7 | AFTER buttons are armed, still before the wake handler runs: `battery_init`, `display_init` (SSD1680 hw reset plus two BUSY waits, `lv_init`), heap log, `lock_gate_check_charge()` (ADC read; on a locked battery a FULL refresh and a network window) | `display_init` is the one to look at: hardware reset + two BUSY waits, plausibly 20-100 ms. Unmeasured | `BOOT_BATT` / `BOOT_DISP` / `BOOT_LOCK` marks; or the `free heap after init` log stamp minus the first app log stamp |
| 8 | `wake_flow_handle_wake` reads the wake cause and the button (first point a pressed button is acted on), then the paint (partial refresh ~0.3-0.5 s, full 1.5-4 s) | the paint dominates what the user sees | NeoPixel ack light, then panel flip |

Observations that matter for the next decision (not acted on, `main.c` is
frozen for this stream):
- The ISR arming (step 6) is already ahead of `display_init` and the battery
  gate, so a press is latched early; what delays its effect is that nothing
  CONSUMES the latch until `wake_flow_handle_wake`, after step 7. The owner
  feels the sum of steps 0-8 up to the first visible/LED reaction.
- Steps 2 and 3 are outside the app and total the bulk of the latency if the
  estimates hold: validation (stays) and the PSRAM test (removed here).
  Everything in `app_main` before the wake handler is likely a small share.
- The flash is run DIO at 80 MHz. QIO would roughly double the read bandwidth
  that step 2 and cache misses use, if the part supports it. NOT changed
  here (flash mode also affects the bootloader and every reflash; separate
  decision, needs the owner's flash chip datasheet).
- Cheapest first measurement: bench build before and after the W1 commit and
  compare the first app log stamp (ms since reset). Second: a spare GPIO
  toggle at `app_main` entry against the wake pad edge on a logic analyser, in
  a local patch that is not committed.

### 5. `COMPILER_OPTIMIZATION_SIZE` (-Os) + `MBEDTLS_COMPILER_OPTIMIZATION_PERF` — ACCEPTED, NEEDS A BENCH SOAK

Two symbols, one commit, because the first is wrong without the second.

- Before: 1,484,176 B (-Og). After: 1,394,128 B (-90,048 B), 76.0 % of the
  slot (165,628 B under the 85 % guard). 0 compiler warnings. Host tests
  54/54 (they do not compile firmware flags, so they say nothing about -Os).
- **Prerequisite fix, own commit (`fix(date_fmt)`)**: the first -Os build did
  NOT compile. `include/date_fmt.h` `date_fmt_iso()` snprintf'd into an
  11-byte buffer; at -Os GCC inlines it into callers and cannot bound the
  `int` fields, so `-Werror=format-truncation` failed the four
  files that include it via `time_util.h` or directly (`timer.c`,
  `timer_persist.c`, `app_state.c`, `wake_flow.c`). The fix formats into a 40-byte scratch and
  copies with the same truncation; same bytes out, five characterization
  tests added to `test_time_util` first and green on the old code. No other
  warning appeared.
- **Trap found and worked around (the reason for the second symbol).** The
  first -Os build was 1,518,096 B, LARGER than -Og by 33,920 B. The map said
  mbedTLS archives had grown 139 KB. Cause, from `build/compile_commands.json`:
  IDF 6.0.1 configures with `CMAKE_BUILD_TYPE=Debug`, and
  `mbedtls/CMakeLists.txt` adds `$<$<CONFIG:Debug>:-O0 -g3>` to its targets.
  mbedTLS's own `-Os` (from `MBEDTLS_COMPILER_OPTIMIZATION_SIZE`) used to
  win by coming last (`-Og -O0 -Os`); with a global `-Os` CMake drops the
  duplicate target `-Os`, leaving `-Os ... -O0`: **mbedTLS compiled at -O0**.
  Only visible with -Os, invisible at -Og. Setting
  `MBEDTLS_COMPILER_OPTIMIZATION_PERF` puts `-O2` last. Effect on the map
  (before -Os, mbedTLS at -Os, vs now): libmbed-builtin +10.7 KB,
  libtfpsacrypto +6.4 KB, libmbedtls -7.7 KB; lwip -13.0, lvgl -12.1,
  wpa_supplicant -11.9, libmain -11.4, esp_hw_support -6.1. mbedTLS is now
  -O2 not -Os; if the owner wants it smaller the choice is to override
  CMAKE_BUILD_TYPE, which I did not touch (changes every component).
  Stated plainly: this works around an IDF build-system behaviour and I did
  not check it against IDF master.
- Sections after (-Os / mbedTLS -O2): `.flash.text` 876,108, `.flash.rodata`
  404,620, `.iram0.text` 89,512 (was 97,212 at -Og), `.dram0.data` 17,235,
  `.dram0.bss` 47,640.
- sdkconfig diff (25 lines, all accounted for): `COMPILER_OPTIMIZATION_DEBUG`
  y -> not set, `COMPILER_OPTIMIZATION_SIZE` not set -> y (their `# default:`
  markers dropped); the deprecated aliases
  `OPTIMIZATION_LEVEL_DEBUG`/`COMPILER_OPTIMIZATION_LEVEL_DEBUG`/

  `MBEDTLS_COMPILER_OPTIMIZATION_SIZE` y -> not set and
  `MBEDTLS_COMPILER_OPTIMIZATION_PERF` not set -> y. Assertion level unchanged

  `# default:`, so `idf.py reconfigure` is the only step on another checkout.
