# Emptying main.c — forcing the wake orchestration under TDD

Status: reviewed — comments resolved, ready for implementation
Branch: `feature/refactor-main`, to be cut from **`integration`** — the live
line. Not `main`, which is 46 commits behind it (and 18 ahead on a divergent
tail).
Predecessor: `refactor/main-orchestrator` — the previous extraction round
(`d042341` alerts, `ce70f92` net_apply, `fe8a2b2` wake_policy, `691a1bd`
app_state), which reached the current line via `integration`
Baseline: `integration` at `4363359`, `main/main.c` = 1342 lines (after
`407c970` merged `feature/break-eligible`). All line references below are
against that revision.
Motivation: "the main.c bugs keep hitting us"

## Problem

`main/main.c` is 1342 lines — 18% of the project's C source, and the single
largest file by a factor of 1.5 over `timer.c`. It is the **only** file of its
size with no host test at all. Everything it does is reachable exclusively by
flashing hardware and waiting for the right wall-clock moment to arrive.

The suite around it is otherwise strong: 23 host suites, sanitizer-armed,
single-TU, covering `timer`, `schedule`, `wake_policy`, `sleep_plan`,
`net_apply`, `app_state`, `bedtime`, `battery`, `quiet_hours` and the display
goldens. The tested modules are the ones that were *extracted from main.c*.
main.c is what is left over — and by construction, what is left over is
whatever nobody found a seam for.

That leftover is not inert plumbing. It is the wake orchestration: the order in
which rollover, bedtime, break-drain, sync, grid-wait, tick, render, latch-drain
and event-watch run, and what each is allowed to observe. That ordering is the
product.

### Extraction alone does not hold — main.c refills

The previous round already did this once, and the file grew back:

**+224 lines, +20%, in twelve days.** Not one of those lines was reviewed
against a rule that asked whether it belonged there, because no such rule
existed. Every feature since paid its orchestration cost into the one file with
no tests, because that is the path of least resistance and nothing pushed back.

This is why the plan has two halves, and why the second is the durable one:
extract the orchestration (tasks 0–12), **and** hold the line with a residency
rule that makes the next 224 lines argue for themselves at review time. The rule
is already live (see below); the extraction is what remains. Doing only the
first half buys about twelve days.

**Twelve of the twenty fixes are ordering defects in the wake orchestration.**
Every one of them is a sequencing question — *what runs before what, and what is
that step allowed to see* — that a host test could have pinned in a dozen lines,
and that hardware testing catches only when the right minute of the right day
happens to arrive while someone is watching.

Now cross-check that against the ten helpers nominated for extraction:

> `status_leds_quiet`, `stats_collect`, `handle_break_end`,
> `post_stats_snapshot`, `config_caches_invalidate`, `run_locate_alarm`,
> `neopixel_show_timer_state`, `make_state`, `check_charge_lock`,
> `minutes_of_day`

**Exactly one of those ten — `handle_break_end` — has ever carried a fix
commit.** The other nine are the cheapest, safest, most obviously-pure code in
the file, and they have never broken. They are worth moving, and this plan moves
them, but moving only them would leave every square inch of the actual defect
surface exactly as untested as it is today.

The list was assembled in file order as evidence of a pattern — *a lot of code
is living in main.c that shouldn't* — and that read is correct. What the fix
history adds is the **extent** of it: the pattern reaches well past the pure
helpers that make it visible, into the sequencing that the helpers are called
from. So the ten are the symptom, and this plan treats them as such — moved
early and cheaply — while the target proper is `handle_timer_tick`,
`handle_button_wake`, `watch_final_minute`, `watch_break_end`,
`finish_action_and_render` and `dispatch_button_action`: roughly 400 lines of
pure sequencing that today cannot be executed off-device at all.

## The residency rule

One sentence, and it is the whole point of the exercise:

> **main.c may contain wiring and device calls. It may not contain a decision.**

An `if` in main.c that is not a null-guard on an injected pointer, or a direct
translation of a hardware datasheet requirement, is a bug waiting to happen in
the one file where nobody can write a test for it.

This rule is **already live** in `.claude/CLAUDE.md` under Process Rules, applied
2026-07-29 ahead of the extraction so that any main.c growth between now and
task 13 is caught at review too. Task 13 is the residency *audit* that settles
up against it.

## Target architecture

Three layers, of which the first two already exist and are proven:

1. **Pure policy** — `wake_policy`, `sleep_plan`, `bedtime`, `quiet_hours`,
   `battery_policy`, `button_actions`, `button_latch`. Total functions over
   scalars. Already host-tested.
2. **Stateful orchestration** — `timer`, `net_apply`, `schedule`, `config_apply`.
   Owns RTC/NVS state, sequences policy calls, calls module APIs for effects.
   Already host-tested via single-TU include with link-time stubs.
3. **Device drivers** — `display`, `neopixel`, `audio`, `buttons`, `battery`,
   `net_window`, `hal_nvs`. Touch silicon.

main.c today is a fourth, unnamed layer holding orchestration that never got
promoted to layer 2. **This plan promotes it.** Nothing new is invented: the
`net_apply.c` extraction (`ce70f92`) is the exact template — a stateful
orchestrator, host-tested by single-TU include, with device effects resolved at
link time or injected.

A note on what that precedent does and does not prove. `net_apply` has taken one
`fix:` since extraction, and that commit (`aa8be4c`) was a main.c ordering fix
that only incidentally touched it. That is too small a sample to claim a
defect-rate reduction, and this plan does not. What the precedent establishes is
**structural**: the seam works, the single-TU harness handles a stateful
orchestrator with real device dependencies, and 457 lines of `test_net_apply`
exist as the worked example to copy. The argument for the extraction rests on
the twelve ordering defects catalogued above, not on extrapolating from
`net_apply`'s quiet quarter.

## Verdicts on the ten nominated helpers

Eight are straightforward pushes. Two need a real answer:

**`run_locate_alarm` — "is literally a passthrough to `alert_run_locate`? Could
be dropped?"** Not a passthrough: it *binds* `extend_awake_failsafe`, adapting
`alert_run_locate(void(*)(int))` to the ops struct's `void(void)`. So it cannot
just be deleted — but it can be *eliminated*, by a different move. Give
`alerts.c` a one-time installer:

```c
void alerts_set_extend_awake(void (*cb)(int seconds));   /* called from app_main */
```

Then `alert_run_locate` takes no argument and `.on_locate = alert_run_locate`
binds directly. Net −4 lines, one less indirection, and the awake-failsafe
extension becomes a property of the alert engine (where it belongs) rather than
a parameter every caller must remember to thread. **Verdict: droppable, via the
alerts installer — not by deletion.** *(Approved at review — task 12.)*

**`stats_collect` / `post_stats_snapshot` / `make_state` / `minutes_of_day` /
`status_leds_quiet` / `neopixel_show_timer_state` / `config_caches_invalidate`.**
All correct to move, all low-risk, none has ever carried a bug. They are the
warm-up phase: they establish the module boundaries and the test harness that
the high-value extractions then ride on. Do them first *because* they are cheap
and safe, not because they are where the risk is.

*Confirmed at review:* the nomination list was written in the order the
functions appear in the file, as **evidence of a pattern** — "a lot of code is
living in main.c that shouldn't" — rather than as a scoping proposal. The
diagnosis above agrees with that reading and measures how far the pattern
actually extends. So the two are not in tension: the ten helpers are the
visible surface of the pattern, and the twelve ordering defects are its cost.

## Two hard design problems

### 1. `enter_deep_sleep()` does not return

Eight call sites depend on this, and eight comments say so ("may not return",
"no return", "does not return"). It is the single biggest obstacle to testing —
a test cannot assert on a function that never comes back — and independently a
standing reasoning hazard, because control flow silently terminates in the
middle of a call tree.

**Fix: make the orchestration return an outcome instead of sleeping.**

```c
typedef enum {
    WAKE_SLEEP_NORMAL = 0,  /* planner picks the interval; buttons armed */
    WAKE_SLEEP_CHARGE_LOCK, /* fixed 600 s, no button wake */
    WAKE_SLEEP_BEDTIME,     /* fixed 7200 s, no button wake */
} wake_sleep_mode_t;

wake_sleep_mode_t wake_flow_run(bool button_wake);
```

Every internal step returns a `bool done` / mode pair and propagates. `app_main`
becomes:

```c
wake_sleep_mode_t mode = wake_flow_run(causes & BIT(ESP_SLEEP_WAKEUP_EXT1));
enter_deep_sleep(mode);
```

One sleep call site instead of eight. In tests, sleep is simply a return value
to assert on. As a bonus the "charge lock wins over bedtime by ordering" rule
(currently an if-order inside `enter_deep_sleep`, lines 205–218) becomes an
explicit tested value rather than an emergent property of statement order.

The awake-failsafe path still needs to force sleep from `esp_timer` context and
keeps calling `enter_deep_sleep(WAKE_SLEEP_NORMAL)` directly — that one is a
genuine "does not return", and it is the only one left.

### 2. RTC-persistent state must survive the move

Four `RTC_DATA_ATTR` variables move out of main.c. This is already a solved
problem: `esp_compat.h:23` defines `RTC_DATA_ATTR` away for host builds, and
`timer.c` — which owns `g_rtc_state` — is host-tested by single-TU include. The
moved state follows the same pattern, and each new module gets a
`*_reset_for_test()` (or the suite zeroes the statics directly, as `test_timer`
does) so cases start clean.

## Test seam

**No new ops struct.** `net_apply`'s `net_apply_ops_t` exists because the
effects it needed (`on_locate`, `on_active_expired_alert`, `post_stats`) were
main.c-local composites it could not call. Once `wake_flow.c` *absorbs* those
composites, they stop being main.c-local, and the need evaporates. `wake_flow.c`
calls `display_*`, `neopixel_*`, `audio_*`, `battery_*`, `net_apply_*` directly.

Host tests use the established single-TU pattern (`test_net_apply` is the
reference, `test/test_net_apply/test_net_apply.c:1-110`):

```c
#include "../../main/timer.c"      /* the real state machine */
#include "../../main/wake_flow.c"  /* the unit under test */
#include "mock_hal_time.c"
/* link-time stubs, each recording into a spy struct: */
void display_full_refresh(const display_state_t *st) { spy.full++; spy.last = *st; }
void neopixel_status_pixel(int i, uint8_t r, uint8_t g, uint8_t b) { ... }
bool alert_run(alert_kind_t k) { spy.alerts[k]++; return spy.dismiss; }
...
```

An ops struct would itself be untested wiring in the one file that cannot be
tested. Link-time stubbing keeps the production call graph literal.

`vTaskDelay` becomes `hal_delay_ms()` (new, alongside `hal_time_now`) so the
watch loops run instantly on host and the suite stays fast.

### The differential sweep is checked in, not scratch

Through cycle 9 the sweep was rebuilt in a temp directory each cycle and thrown
away. That made everything it uniquely covers — clock-read count and position,
argument-level ordering, operands living inside log varargs that the host build
discards — unprotected the moment the directory was cleaned. Cycle 9's one real
escape landed in exactly that gap.

From cycle 10 onward the sweep is built **in-repo** under `test/difftest/` and
committed with the cycle it validates. `test/difftest/run.sh <cycle>` enforces
the two-sided invariant: the control must report zero divergences, and every
perturbation must report a non-zero count. A perturbation that reports zero is
a failure — it means the sweep is blind on that axis and the control proves
nothing there. See `test/difftest/README.md` for what the sweep does and does
not prove.

## The adversarial review rule

Live in `.claude/CLAUDE.md` under Process Rules since 2026-07-29, reproduced
here so the plan is self-contained:

> **main.c is under adversarial review.** Any diff that adds a line to
> `main/main.c` must justify, in the review, why that line cannot live in a
> host-tested module. main.c is the one file with no test coverage, and 12 of
> its 20 historical fixes were ordering defects a host test would have caught.
>
> The only admissible reasons for residency are:
> 1. **Boot ordering is a hardware contract** — the NeoPixel gate, NVS init, TZ,
>    `timer_defs_install()` sequence in `app_main`.
> 2. **It runs in an interrupt or `esp_timer` context** where the module API is
>    not safe.
> 3. **It owns an ESP-IDF handle** with no module home (`esp_timer_handle_t`,
>    `gpio_hold_en`, `esp_deep_sleep_start`).
> 4. **It is a ≤3-line thunk** adapting a module ABI to another module's
>    callback signature, containing no branch.
>
> "It's only a few lines", "it's obviously correct", and "it's just plumbing"
> are **not** admissible. An `if` in main.c that is not a null-guard on an
> injected pointer is a review blocker. If the reviewer cannot name which of the
> four reasons applies, the code moves.

## Risks

- **Scale.** ~1200 lines relocate. Mitigated by strict phase ordering, each
  phase independently shippable and green, and by extracting *behaviour-first*
  (tests pinning today's behaviour before the move, so a phase that changes
  behaviour fails immediately).
- **The sleep-outcome refactor (task 5) touches every path.** It is a pure
  control-flow change with one new test, landing before any logic moves, so a
  regression here is isolated and bisectable.
- **Display goldens.** No layout change is intended; any golden diff during this
  work is a real regression and must not be regenerated (CLAUDE.md invariant).
- **Hardware smoke test is still required** after tasks 6, 11 and 13: a full
  day-cycle run covering rollover, a break, an expiry, a bedtime lock and a
  charge-lock release. Host tests pin ordering, not silicon.

## Non-goals

- No behaviour change. This is a pure test-coverage and structure exercise; any
  behaviour delta discovered mid-flight gets its own commit and its own row in
  the table above.
- No change to the refresh-policy / panel-protection split (CLAUDE.md
  invariant).
- Not merging `wake_flow.c` into `net_apply.c`. They are different windows of
  the same wake and the split is load-bearing.
