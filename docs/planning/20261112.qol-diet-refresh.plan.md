# QoL, firmware diet, refresh cadence, multi-sprite, IDF updates — plan

Owner request 2026-11-12. Six workstreams, run one at a time by an
orchestrator. Baseline is `integration` at `3d3427c`, IDF v6.0.1.

## How the work runs

- **Cycle per workstream:** implementor (Sonnet) → adversarial reviewer
  (Fable) → separate fix agent (Sonnet) → reviewer re-check if the fixes were
  non-trivial. Orchestrator merges the branch into `integration` locally.
  Nothing is pushed.
- **One plain feature branch per workstream**, off `integration`. No
  worktrees (the streams are sequential).
- **Rate limits are expected.** Every agent keeps
  `docs/planning/20261112.<stream>.notes.md` up to date (done / in progress /
  next step / measurements) and makes WIP commits on its branch as it goes
  (`chore(wip): …` is fine; Conventional Commits are hook-enforced). A resumed
  agent starts from the notes file and `git log`, not from scratch.
- **Every brief repeats:** TDD first; edit files with the Edit/Write tools,
  never scripted text edits; Python tools use PEP 723 + `uv run`; build with
  `bash -lc "source ~/esp/esp-idf/export.sh >/dev/null 2>&1 && idf.py build"`;
  run `idf.py reconfigure` before building after any Kconfig change;
  never delete `sdkconfig` (snapshot it first); `clang-format` must pass; the
  `main/main.c` residency rule; grep the whole tree before editing any comment
  or doc that states a value.

change is not tangled with any behaviour change.

## Decisions — settled, do not re-litigate

1. **Refresh cadence is a Kconfig value**, default 10. No HA entity, no NVS.
2. **The ack hold is removed for both the chore ack and Button B**
   start/resume. The Kconfig knob and its check script are retired.
3. **Sprite variant is picked once per lock episode**, not per paint.
4. **Button C feedback is a binary count on the four NeoPixels**: the
   1-based timer number, **least significant bit on the physically leftmost
   pixel** (owner-confirmed 2026-11-12). Timer 1 (Screen) lights the
   leftmost pixel, timer 2 the one to its right, timer 3 both, and so on, up
   to 15 timers.
   The strip runs opposite the buttons: the leftmost pixel, over button A,
   is driver index 3, and index 0 is rightmost, over button D
   (`main/status_led.c`, the `k_chore_pixel` comment; board-verified
   2026-09-22). This is the same convention the last-15-seconds countdown
   already uses: `neopixel_status_binary4()` puts bit 0 on index 3 and the
   MSB on index 0 (`include/neopixel.h`). **Reuse that function; do not
   write a second bit-to-pixel mapping and do not "fix" its shift.**
5. **Mode switches (Timers ↔ Chores) keep forcing a full refresh.**
6. **Image validation on every wake stays** (`BOOTLOADER_SKIP_VALIDATE_IN_DEEP_SLEEP`
   remains off). It is not a candidate and is not to be measured against.
7. **IPv6 is dropped.** TLS client stays (OTA). TLS *server* is dropped only
   if setup mode is proven not to use it (see stream A).
8. **The ack hold's visible delay goes, its incidental debounce is replaced
   explicitly** by a same-button refractory window in `button_latch` (see
   stream B).
9. **A timer swap stays a partial refresh**, as it is today (see stream C).

## Stream B — remove the ack hold

The delay the owner feels is `STATUS_LED_ACK_HOLD_MS` (400 ms): the old
colour is held before the first pixel flips.

- Sites: `main/wake_flow.c` ~855 (chore ack, first ack of the wake) and
  ~1780 (Button B start/resume). Both `hal_delay_ms(STATUS_LED_ACK_HOLD_MS)`
  calls go.
- Retire `CONFIG_MAGTAG_STATUS_LED_ACK_HOLD_MS` (`main/Kconfig.projbuild`),
  the `STATUS_LED_ACK_HOLD_MS` macro (`include/status_led.h`),
  `scripts/check-ack-hold-default.py`, its pre-commit hook entry and
  `test/test_check_ack_hold_default`. Changing only the default would do
  nothing on an existing checkout: the owner's `sdkconfig` holds an unmarked
  `=400`, which wins.
- `CHORE_WORST_GESTURE_MS` and the final-minute static asserts in
  `wake_flow.c` include the hold; rework the sums.
- Tests: the `test_wake_flow` cases that pin the hold (e.g.
  `test_t8_the_ack_hold_is_one_figure_shared_with_button_bs_start`) are
  rewritten to pin its absence: the strip paint follows the apply with no
  delay call in between, on both paths.
- Comments and docs that describe the hold (wake_flow.c, status_led.h,
  Kconfig help, `docs/behavior/chores.md`, architecture pages) are updated in
  the same branch.
- **Debounce the hold was providing by accident.** `button_latch` owns
  debounce (50 ms chatter window, release gate, 10 ms release settle), but
  the gate only learns a button is up from a level sample, and nothing
  samples during the 400 ms hold. So today the wake button's release, and its
  bounce, normally happen while nobody is looking and are rejected. With the
  hold gone the coalescer samples every 50 ms from the start; a sample can
  land in a high phase of the release bounce, and a bounce edge more than
  10 ms later is then accepted as a second press. On a chore that is a
  phantom un-tick; on Button B a phantom re-pause.
  Replace it explicitly, in `button_latch.c` with host tests first: after a
  press on button N is accepted (including the EXT1 wake press, which must be
  seeded into the latch at reset), edges on **the same button** are ignored
  for a refractory window (start at 300 ms; one named constant). Other
  buttons are unaffected, so a second chore can be ticked immediately, which
  is the lag being removed. A deliberate same-button re-press faster than
  the window is lost; that is the accepted cost. Bench check on the device:
  20 single taps on each chore button, none may double-toggle.
- Not in scope: `CHORE_PAINT_QUIET_MS` (1200 ms) and the burst budget. They
  delay the panel paint, not the buttons. If the gesture still feels laggy
  after B and A, the remaining lag is wake latency (stream A).

## Stream A — firmware diet and wake latency

Baseline measured 2026-11-12 on `3d3427c` with the owner's `sdkconfig`:
`magtag_timer.bin` is 1,541,440 B of a 1,835,008 B slot (84.0 %; the guard
in `tools/check_slot_size.py` is 85 %). Flash code 992,846 B, rodata
426,980 B.

Method: one candidate per commit. For each, record in the notes file the
image size before/after, whether host tests and display goldens stay green
(goldens must be byte-identical; no regeneration), and whether the feature
it touches still has a consumer. A candidate that cannot be shown unused is
dropped, not forced. Each accepted symbol goes into `sdkconfig.defaults` and
the notes say what the owner must do to their local `sdkconfig` to pick it
up (precedence rule in `docs/developer_setup.md`).

Size candidates, with the evidence that put them on the list:

| Candidate | Evidence | Check before accepting |
|-----------|----------|------------------------|
| `COMPILER_OPTIMIZATION_DEBUG` (-Og) → `SIZE` (-Os) | sdkconfig is on the debug default; 993 KB of code | Stack high-water marks, the OTA timing asserts, a soak on the bench |
| Fonts | glyph bitmaps are 92 KB (48) and 32 KB (28); 5 kerning tables of 3 KB each; all 4 bpp | Handled in its own sub-stream, A2 below |
| `LV_DRAW_SW_COMPLEX` off | `lv_draw_sw_box_shadow` (3 KB) is linked; noted as unmeasured in `sdkconfig.defaults` | Goldens byte-identical |
| IPv6 off (`LWIP_IPV6`) | `nd6_input` is linked; no IPv6 use in `main/` | Owner-approved. Build, then one MQTT + SNTP + OTA-check wake on the bench |
| mbedTLS server side off (`MBEDTLS_TLS_CLIENT_ONLY`) | `mbedtls_ssl_handshake_server_step` (4 KB) is linked. Setup mode does not appear to use it: `ESP_HTTPS_SERVER_ENABLE` is off, protocomm is security 2 (SRP6a over plain HTTP), and nothing in `main/`, network_provisioning or protocomm references an HTTPS server | Accept only after a full setup-mode run on an erased-NVS device: AP + QR, phone provisioning, MQTT form, first connect. TLS client stays (OTA uses `ota_ca.pem`) |
| WPA3 SAE / OWE / SoftAP SAE | enabled by default | Owner's AP security mode; ask before dropping |
| `ESP_ERR_TO_NAME_LOOKUP` off | enabled by default | Log lines that print `esp_err_to_name` degrade to numbers |
| Log strings | 140 KB of merged string literals | Only if the above is not enough: `LOG_MAXIMUM_LEVEL`, or trimming the longest strings |
| scanf family | `vfscanf` (2.6 KB) is linked | Find the caller |

Not candidates: coredump (hand-set locally, not in the defaults), anything
OTA rollback depends on, per-wake image validation (decision 6), the LVGL
widgets already trimmed.

### A2 — 1-bit fonts (own branch `feat/one-bit-fonts`, after A)

The five Montserrat sizes in use (12, 16, 18, 28, 48) are LVGL's stock
4 bpp anti-aliased builds, each carrying the full ASCII range plus about 60
FontAwesome symbols. On a 1-bit panel the anti-aliasing is thresholded away,
which is what makes stems uneven. LVGL ships only two 1 bpp fonts,
`unscii_8` and `unscii_16`: an 8x8 terminal face, crisp but crude, and with
no size near 28 or 48. So the fix is generated fonts, not a Kconfig switch.

- Generate project-owned 1 bpp fonts with `lv_font_conv --bpp 1`, restricted
  to the glyphs each size actually draws (48 is very likely digits and
  colon only; the symbol set shrinks to the battery/status glyphs used).
  Commit the generated `.c` files and a regeneration script (PEP 723 + uv,
  or the documented npx command); the build must not need Node.
- Candidates to compare, same sizes: (a) Montserrat at 1 bpp with strong
  autohinting; (b) a face drawn for the pixel grid at the small sizes (12,
  16, 18), keeping a hinted outline face for 28 and 48. The implementor
  proposes two or three licence-compatible faces; the investigator checks
  what `lv_font_conv` accepts as input before promising a bitmap-strike font.
- Evaluation is by eye on the panel: the agent produces a host-rendered
  contact sheet (PNG from the golden renderer) per candidate, and a firmware
  build per finalist for the owner to flash. **The owner picks.**
- This is an intentional layout change: label metrics move, the fit ladders
  in `display_screens.c` need re-checking, and every golden is regenerated
  once, for the chosen font only, with the diff reviewed.
- Expected saving is large (4 bpp to 1 bpp is a quarter of the bitmap before
  subsetting) but is to be measured, not assumed.

Wake latency (deep-sleep wake to "button presses are accepted"):

1. **Measure first.** Add or reuse a log line giving microseconds since boot
   at the point the button latch ISR is armed and at the first dispatch.
   Bootloader time is not visible from the app; estimate it from the wake
   pin edge to the first pixel change with the owner's help, or from the
   bootloader's own timestamps before they are silenced.
2. Candidates, cheapest first:
   - `BOOTLOADER_LOG_LEVEL` INFO → WARN or NONE; `BOOT_ROM_LOG` off where
     the option is efuse-free. Blocking UART text on every wake.
   - `SPIRAM_MEMTEST` off: a 2 MB memory test on every wake. Also establish
     whether anything needs PSRAM at all; if not, skipping its init on a
     deep-sleep wake is a further saving.
   - Arm the button latch earlier in `app_main`, if the measurement shows
     the app side is the larger share. `main.c` is under adversarial review:
     any new line needs one of the four residency reasons.
   - Per-wake image validation is **not** a candidate (decision 6). It does
     mean a smaller image wakes faster, since the hash is over the whole
     image: record wake latency against image size as the diet proceeds.
3. Report: a before/after table of size and wake latency in the notes file,
   and the list of local-`sdkconfig` lines the owner must touch.

## Stream C — Button C counted clicks

Today: a C press in Timers mode calls `timer_select_next()` once
(`wake_flow.c` ~1865) and paints. **The paint is already a partial**: a
button wake rides the partial cadence (`wake_policy_render`, `button_wake`
arm), and `selection_changed` only suppresses the expiry alert. A swap is
promoted to a full refresh in three cases only, all of which stay:
the swap crosses the Screen Break layout (a full-screen inversion), the
screen kind otherwise changes (`display_screen_for` before vs after, or a
lock screen was on the glass), or the paint happens to be the Nth of the
cadence (5 today, 10 after stream D). Presses made during the paint
collapse into at most one more swap and a second paint.

Target behaviour:

- The first C press (the wake press, or a latched one) opens a **count
  gesture**. The candidate starts at the next enabled timer. Each further C
  press within a sliding quiet window advances the candidate to the next
  enabled timer, wrapping through Screen.
- After every press the strip shows the candidate's number in binary
  (decision 4). The number is the timer's ordinal among enabled timers,
  Screen = 1.
- When the quiet window lapses, the candidate is committed once
  (`active_slot` moves once) and the panel is painted once, through the
  same render decision a single swap uses today (partial unless one of the
  three promotions applies). Landing back on the starting timer commits
  nothing and paints nothing.
- Unchanged: C is refused while the active timer is RUNNING; C in Chores
  mode is still ✓2; a swap during a Screen Break is still allowed; landing
  on an EXPIRED timer does not re-fire its alert.

Design constraints for the implementor:

- **Policy is host-tested, outside `main.c` and as far as possible outside
  the `wake_flow.c` orchestration:** a pure "advance candidate" function
  next to `timer_next_slot()` in `timer.c` (candidate in, next enabled slot
  out, no state write), and a pure `status_led` function mapping a timer
  ordinal to four pixels, tested like `chores_led_for()`.
- The wait loop mirrors the chore coalescer
  (`wake_flow_coalesce_chore_acks`): a quiet window and a hard budget, both
  Kconfig (`MAGTAG_SWAP_COUNT_QUIET_MS`, suggested default 700;
  `MAGTAG_SWAP_COUNT_BUDGET_MS`, suggested default 6000), with a static
  assert against `MAGTAG_MAX_AWAKE_SEC` like the chore gesture's.
- Presses of other buttons during the gesture stay latched and are drained
  afterwards by the existing paths; they do not end or join the gesture.
- The strip has a documented list of claimants (`include/status_led.h`,
  "five claimants") and a wrapper check
  (`scripts/check-status-led-wrapper.py`). The count display is a new
  claimant: add it to that contract, including what the strip returns to
  after the commit and how it behaves in quiet hours (follow what the chore
  strip does for a press-driven paint).
- Tests in `test_wake_flow`: one press = today's behaviour; N presses = one
  commit, one paint (partial in the ordinary case); wrap; a full lap = no commit, no paint; refused
  while RUNNING; chore mode untouched; budget exhaustion commits what it
  has.
- Docs: `docs/behavior/timers_and_schedule.md` and the peripherals page.

## Stream E — multiple sprites per lock screen

The art is tiny (RLE: bedtime 60 B, break 205 B, charge 787 B, time's up
981 B), so this does not depend on stream A.

- **Generator** (`tools/gen_sprites.py`, `tools/sprites/`, `sprites.local/`):
  accept `<slot>.png` plus `<slot>.<n>.png` variants in both the template and
  the override directory. Every variant of a slot must fit the slot's
  existing box (the layouts use `SPRITE_*.w/.h` and literals such as
  `TIMESUP_COL_X`), so the generator rejects a variant with different
  dimensions. Emit a per-slot table and count, e.g.
  `const sprite_t *const SPRITE_CHARGE_VARIANTS[]` and
  `SPRITE_CHARGE_VARIANT_COUNT`. Decide and document whether override
  variants replace or extend the template's. `test/test_gen_sprites` first.
- **Pick** (new host-tested module, e.g. `sprite_pick.c`): given a slot, its
  variant count and a random source, return the variant for the current lock
  episode. The pick is made when the lock screen kind changes into that
  screen and is kept until it changes away; it must survive deep sleep (RTC
  memory). If it goes into `rtc_state_t`, bump `RTC_STATE_VERSION`. The
  random source is injected (a HAL stub over `esp_random()`), so tests are
  deterministic.
- **Screens** (`display_screens.c`): the four `build_sprite(&SPRITE_X, …)`
  calls take the picked variant.
- **Goldens:** with one variant per slot the output must be byte-identical
  to today's; no golden is regenerated. Add render tests for "variant 1
  selected" using a test-only second variant.
- No new art is drawn in this stream. Document the file naming in the
  sprites section of the developer docs.

## Stream F — ESP-IDF and component updates

Known so far: installed IDF is v6.0.1; upstream has v6.0.2, v6.0.3 and
v6.1. The component manager reports `espressif/mqtt` 1.0.0 → 1.1.0,
`espressif/network_provisioning` 1.3.1 → 1.4.0, `espressif/json_generator`
2.0.0 → 2.1.0 (transitive), `lvgl/lvgl` 9.5.0 → 9.6.0~1.

**F1 (research, read-only, Fable):** read the release notes and changelogs
for each and report, per item: fixes that touch what this firmware uses
(ESP32-S2 deep sleep / EXT1, USB CDC console, WiFi, OTA, NVS, SPI, RMT,
mbedTLS), breaking changes, and a take / skip / defer verdict. Specifically
check whether the USB CDC `linker.lf` IRAM bug recorded in
`sdkconfig.defaults` is fixed in 6.0.3 or 6.1. Also report where the IDF
version is pinned (devcontainer, docs).

Orchestrator's starting position, to be confirmed or overturned by F1:
take the newest 6.0.x patch release; defer 6.1 (a minor release, with
Kconfig and size churn) unless it fixes something this device suffers from;
take the mqtt and network_provisioning minors only if their changelogs show
a relevant fix; take LVGL only if every display golden stays byte-identical
and the image does not grow.

**F2 (apply):** one update per commit, `dependencies.lock` committed with
each, full host tests + firmware build + size check after each, and a
`sdkconfig` snapshot/diff around the IDF bump.
