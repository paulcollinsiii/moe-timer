# Architecture

An overview of how the MagTag Screen Timer firmware is built, for a
developer about to change it, and the invariants no change may break. The
pages under [architecture/](architecture/) go one level deeper, one subsystem
each. Setup and build commands are in [developer_setup.md](developer_setup.md);
what the device does from the family's side is in
[product_overview.md](product_overview.md).

## The Wake Cycle

The device is an ESP32-S2 that deep-sleeps almost all the time. Every wake,
whether from its timer, a button or a power-on, is a fresh boot through the
same path:

```
 deep sleep ──(RTC timer, or a button on EXT1)──▶ reset ──▶ app_main()

 boot          LEDs off (GPIO 21 high) → awake failsafe armed (180 s)
               → NVS → time zone → timer state: validate, install definitions, restore snapshot
               → OTA rollback detector → buttons, battery, display
               → charge lock? ──yes──▶ sleep 600 s (the engaging wake paints and syncs once)
                     │
 wake decode   EXT1 bit set? ──yes──▶ button handler
                     └──no (timer, power-on)──▶ tick handler
                     │
 both handlers no SSID + power-on/press, or a BOOT wake? ──yes──▶ setup or sleep
               → day rollover (+ network window, daily OTA check)
               → locks: no clock → Bed Time → config error ──engaged──▶ paint, sleep
               → break-end drain
               → tick: sync if due, wait for the minute │ button: run the press
               → break due? ──yes──▶ paint break screen, sleep
               → render → latched presses → final-minute / break-end watch
               → OTA download, if one was found
                     │
 sleep funnel  enter_deep_sleep(): join window → certify new image → save snapshot
               → wait for release → LEDs off, pads held → arm buttons + next wake → sleep
```

A network window runs on its own task beside the main task. It brings WiFi up,
syncs NTP, rides along an OTA check when one is armed, talks to Home Assistant
over MQTT, and drops WiFi again. Its results are applied on the main task after
it joins.

## System invariants

These hold for the running device at every instant. A change that breaks one
is a bug, whatever its tests say. The `I`-numbers in parentheses are the
names the code uses for the same rules: I1–I5 in `test/test_timer`'s
`assert_state_legal`, I6–I10 in the comments of `timer.h` and `timer.c`.
Rules for whoever edits the code (pure C, component names, golden
regeneration, boot-order obligations) are development rules and live in
`.claude/CLAUDE.md`.

Rows run in reading order: timer state model (S1–S5), break and exposure
(S6–S12), day, clock and chores (S13–S18), locks and buttons (S19–S24),
display and peripherals (S25–S27), network and OTA (S28–S40), sleep, flash
and boot (S41–S47), then setup mode (S48), which spans locks, buttons and
sleep.
