# Architecture Reference

Module map, hardware target, persistent-state layout, and subsystem design notes for the MagTag Screen Timer firmware. For build/flash/test commands see [developer_setup.md](developer_setup.md).

## Hardware Target

| Attribute | Value |
|-----------|-------|
| Board | Adafruit MagTag 2.9" (2025) |
| MCU | ESP32-S2 @ 240 MHz, 4 MB flash |
| Display | 2.9" grayscale e-ink 296×128 px, SSD1680 controller (FPC-7519rev.b, x-RAM offset 0) |
| Buttons | 4× tactile — GPIO 15/14/12/11 (A/B/C/D) (active-LOW, internal pull-up); Button C swaps timer types (v1.3) |
| NeoPixels | 4× RGB on GPIO 1 (power gate: GPIO 21 LOW = on) |
| Speaker | Amplifier shutdown pin GPIO 16 (HIGH = on) |
| No dedicated RTC chip | ESP32-S2 RTC timer used for deep-sleep wakeup |

## Flash Layout

`partitions.csv` is authoritative (`CONFIG_PARTITION_TABLE_CUSTOM`); what is
here is the constraint the table carries, not a second copy of it.

| Partition | Type | Offset | Size |
|-----------|------|--------|------|
| `nvs` | data/nvs | `0x9000` | `0x6000` |
| `phy_init` | data/phy | `0xf000` | `0x1000` |
| `ota_0` | app/ota_0 | `0x10000` | `0x1C0000` (1.75 MB) |
| `ota_1` | app/ota_1 | `0x1D0000` | `0x1C0000` (1.75 MB) |
| `otadata` | data/ota | `0x390000` | `0x2000` |
| `assets` | data/`0x40` | `0x392000` | `0x6E000` (440 KB; the optional alert WAV) |

Two properties of this layout are **one-way**, which is what makes them
architecture rather than build trivia:

- **The slot size is frozen.** An OTA writes an app slot; it cannot rewrite the
  partition table. So the layout shipped with the first OTA-capable firmware is
  the layout those devices keep, short of a serial cable per device. `nvs`,
  `phy_init` and `ota_0` deliberately kept their offsets from the predecessor
  table, so reflashing over an in-service device preserves its config and an
  empty `otadata` still boots `ota_0` at the old factory offset; `ota_1`,
  `otadata` and `assets` all moved when the slots grew, so a device with a
  flashed WAV needs `tools/flash_assets.sh` re-run after reflashing the table.
- **The bootloader is not OTA-updatable.** `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`
  is *not* a bootloader-only symbol — the app is compiled against it too
  (`app_update/esp_ota_ops.c` guards four blocks on it, and `app_update` is an
  app component). The second spelling in a generated `sdkconfig`,
  `CONFIG_APP_ROLLBACK_ENABLE`, is not a second symbol: it is this one's
  deprecated former name, declared in the bootloader component's
  `sdkconfig.rename` and re-emitted for backward compatibility with old
  configs. It says nothing about the app half. But the *decisive* half is
  bootloader-resident: only the 2nd-stage bootloader can mark a `PENDING_VERIFY`
  slot aborted and boot the other one, and switching the option on grows that
  binary (22,640 B off → 22,720 B on). An OTA writes only the app slot, so a
  later update can deliver the app half and never the bootloader half — the
  conclusion stands: rollback protection cannot be switched on after the fact.
  Whatever bootloader a serial flash wrote is the bootloader that device keeps,
  so this had to be settled before any device shipped OTA-capable firmware, and
  it is settled in `sdkconfig.defaults`.

Because the slot size cannot be renegotiated later, the headroom it was chosen
for is guarded at build time: `tools/check_slot_size.py` is wired to the `app`
target from the project-root `CMakeLists.txt` and fails the build once the
image passes `MAGTAG_MAX_SLOT_PCT` (85) of its slot. The threshold is set in
that file and deliberately refuses `-D` on the command line. The image size and
the occupancy it produces are **not** recorded here — they move with every
build; the guard prints the live figure and `docs/planning/ota.plan.md` records
the landing measurement.

## Layer Model

Every module sits in exactly one of three layers, and the layer decides how it is
tested. The numbering is a **testability ladder, not a call graph**: layer 1 is what
a host test can call with nothing stubbed, layer 2 needs link-time stubs for its
effects, layer 3 needs hardware. Layer 2 is the layer that calls *both* ways — it
sequences layer-1 decisions and calls layer-3 drivers for the effects — so "calls go
down only" would be false however the layers were numbered. Very little about the
call direction is actually invariant here; what is, and the shapes that break it,
are set out under the list.

1. **Pure policy** — `wake_policy`, `sleep_plan`, `bedtime`, `quiet_hours`, `battery_policy`, `battery_soc`, `chores`, `button_actions`, `buttons_policy`, `button_latch`, `status_led`, `display_layout`, `display_screens`, `config_validate`, `stats_json`, `tones`, `wav_header`, `mqtt_rx`, `mqtt_topics`, `ota_policy`, `ota_url`, `ota_facts`, `time_util`, `date_fmt` (header-only). Total functions over their arguments: a `time_t` only ever arrives as a parameter (nothing here reads the clock), and no NVS, no GPIO, no ESP includes. Host-tested directly. Layer-1 modules do call each other — `bedtime` → `quiet_hours`, `display_screens` → `display_layout`, `wake_policy` → `sleep_plan`'s constants — which is inside the layer, not up out of it. Two of them also sit behind a layer-3 *header* without being layer-3 code: `battery_soc` implements `battery_percent_from_mv` out of `battery.h`, and `display_layout` implements the `display_bar_fill_px`/`display_format_*` half of `display.h`. `display_screens` additionally compiles against LVGL and uses `localtime_r`/`strftime` to format a time_t it was handed. The three OTA modules each qualify the "no ESP includes" clause slightly differently, and one of them contradicts it outright: `ota_url` composes `config_validate`'s https rule and nothing else, `ota_policy` parses the manifest with the vendored cJSON (as `config_apply` does from layer 2), and `ota_facts` **does** include ESP headers — `esp_ota_ops.h`, `esp_image_format.h`, `esp_tls_errors.h` — for the error *constants* it classifies and for nothing else, which is why the host build can supply them from `test/mocks/esp_compat.h` and test it directly with nothing stubbed.
2. **Stateful orchestration** — `wake_flow`, `lock_gate`, `timer`, `timer_defs`, `timer_persist`, `config_cache`, `config_apply`, `cmd_apply`, `ha_config`, `net_apply`, `app_state`, `alerts`, `schedule`, `ota_flow`. Owns the RTC/NVS state, sequences the layer-1 calls, and calls layer-3 drivers for the effects. Host-tested by single-TU include: the suite `#include`s the `.c` under test and resolves its device effects with link-time stubs (`test/test_wake_flow` is the worked example). `ota_flow` takes it one step further, as `net_apply` does: every device effect arrives through an injected `ota_flow_ops_t`, so `test_ota_flow` runs the real sequence with counters in place of a radio and a panel, over the real `nvs_config.c` against `mock_hal_nvs.c`.
3. **Device drivers** — `display`, `neopixel`, `audio`, `buttons`, `battery`, `light`, `net_window`, `wifi_session`, `ntp`, `mqtt_ha`, `ota`, `ota_task`, `device_id`, `nvs_config`, `chore_store`, `hal_nvs`, `hal_time`, `components/ssd1680`. Touch silicon; verified on hardware ([hardware_smoke_test.md](hardware_smoke_test.md)). `nvs_config` and `chore_store` are the exception in the other direction: they reach flash only through `hal_nvs`, so they are host-tested against `mock_hal_nvs.c` (`test_nvs_config`, `test_chore_store`) and only `hal_nvs` beneath them is hardware-verified. Two of them are here for the ladder's reason rather than the label's: `net_window` and `ota_task` touch no silicon at all, but they are FreeRTOS task mechanics with nothing in them a host suite could call, so hardware is the only place they run. Both are the *task* half of a split whose *sequence* half is host-tested in layer 2 (`net_apply`, `ota_flow`).

**The direction rule.** The rule with the strongest claim across the tree is
**no layer-3 driver calls layer 2** — and even it does not hold. Everything else
people expect to be true here is not, and that rule itself has more breaches than
any short list admits, so both are spelled out rather than asserted:

- A driver calling **layer 1** is normal and pervasive, not an exception — that is
  just a driver reaching for a pure helper, which is what the ladder is for.
  `audio.c` → `tones_*`/`wav_header_parse`, `buttons.c` → `button_latch_*` and
  `buttons_policy_wake_mask`, `mqtt_ha.c` → `stats_json_*`/`mqtt_rx_on_data`.
- Layer 1 is meant not to call *out* at all. Two modules break that.
- Even the one rule is broken, by drivers that reach into layer 2 directly —
  some of them mutators. The list below is **illustrative, not a census**, and
  deliberately carries no total, and no per-driver or per-module count either:
  three consecutive commits shipped a count that was wrong, each while claiming
  accuracy. The source is the authority — re-scan it, never count from here.

Every entry here was found by scanning the call graph, not by reading the previous
version of this section. An earlier draft claimed "calls go down only", and the
draft that replaced it claimed "no layer-3 driver calls layer 2 or layer 1" — both
were false, and both were written in commits whose stated purpose was accuracy. If
you edit this list, re-scan; do not reason from the prose.

The driver→layer-2 calls worth knowing about (illustrative, per the note above):

- `net_window.c`, in `net_window_wait_ntp()` and `net_window_join()` — `timer_record_ntp_sync(time(NULL))`. A **mutator**: the
  driver writes layer-2 state directly. Not the only mutator — `mqtt_ha.c` has
  three of its own, below — but the sharpest, because the state it writes is the
  timer's.
- `net_window.c`, in `net_window_task()` — `ota_flow_check(...)`, the whole manifest-check phase, run
  on the driver's own task. Not a state write but a control-flow inversion:
  layer 3 supplies the thread, layer 2 supplies the sequence. Deliberate — the
  check has to ride the window the wake was already opening, and its device
  effects are still buffered for the main task the way every other
  network→device effect in this tree is.
- `ota_task.c`, in `ota_apply_task()` — `ota_flow_apply(...)`. The same inversion, and this module
  exists for nothing else: it is the dedicated 16 KB task the download needs,
  held apart from `ota_flow.c` precisely so the sequence stays host-testable
  with no FreeRTOS in it. The same split as `net_window.c` to `net_apply.c`.
- `buttons.c` — reads `timer_swap_allowed()` to fill the `buttons_policy`
  input struct. Reads only. It no longer reads `timer_reload_allowed()`:
  Button B is armed unconditionally, so that gate left the struct with it.
- `mqtt_ha.c`, in `publish_discovery()` — reads `timer_slot_def(slot)` to publish discovery. Reads only.
- `mqtt_ha.c`, in `publish_states()` — `ota_flow_stat(&ota)` for the stat payload's OTA leg. Reads
  only, and it has to be read *here* rather than carried in the snapshot; the
  OTA reporting note below says why.
- `mqtt_ha.c` is the densest caller, and an "exceptions" framing hides it.
  Besides the two above it drives the whole `ha_config` registry —
  `ha_config_discovery_gate()` from `publish_states()`, the registry's
  discovery documents from `publish_config_discovery()`,
  `ha_config_json_escape()` from `publish_action_discovery()`, and
  `ha_config_set()` plus `ha_config_state_json()` from `apply_sets()` — and
  applies both retained HA documents (`config_apply` and `cmd_apply`, both
  from `apply_incoming()`). Named by function rather than line: the line
  numbers that stood here had all drifted.
  `ha_config_set`, `config_apply` and `cmd_apply` are **mutators**. This is not
  an oversight: the HA session is where those documents arrive, and the parsing
  and validation they delegate to is layer 1 and host-tested — but it does mean
  the driver→layer-2 edge is an ordinary shape in this file rather than a short
  list of exceptions.

And the two layer-1 modules that call out, listed here rather than reclassified or
defined away, because in both cases the pure table is what the tests are about and
the impure call is one line over it:

- `status_led.c` — `status_led_for_state()` is a pure state→RGB table. `status_led_show_timer_state()` takes no arguments: it reads `timer_get_state()` (layer 2) and drives `neopixel_status_pixel()` (layer 3). One call up and one call down, in a four-line function.
- `button_actions.c` — the outcome map is a pure decision table, but it applies itself: `button_b_apply()` branches on `timer_get_state()` and then calls `timer_pause`/`timer_start`/`timer_resume`/`timer_reload`, which are layer-2 **mutators**. `button_b_start_allocation()` likewise reaches `timer_active_def()` and `schedule_*`. `test_button_actions` stubs timer and schedule to test it, which is layer-2 treatment for a layer-1 file.

`main/main.c` is none of the three — it is the **composition root**. It may hold wiring and device calls but may not hold a *decision*: a line survives there only by naming one of four residency reasons — (1) boot ordering is a hardware contract, (2) it runs in ISR/`esp_timer` context where a module API is not safe, (3) it owns an ESP-IDF handle with no module home, (4) it is a ≤3-line branch-free thunk adapting to another module's callback signature. The rule is in `.claude/CLAUDE.md` and is quoted, not paraphrased: an earlier draft of this line read "handle *or call*", which is a widening that exists nowhere in the rule and which was admitting three render seams. With it restored, `make_display_state` and `paint_current_state_full` could name no reason and moved to `wake_flow.c`. main.c's own header comment names the reason for every symbol left in it, and names the one branch that has no reason (the button-release wait in `enter_deep_sleep`) as debt rather than labelling it. The extraction that produced this shape (1342 → 354 lines, of which 131 are code) is `docs/planning/implemented/20260729.refactormain.plan.md`. The OTA feature added no line that needed a new reason and no decision: two branch-free thunks (`ota_session_begin`, `ota_mono_ms` — reason 4), the `OTA_FLOW_OPS` table (wiring, with nothing to execute, the same standing as `NET_APPLY_OPS`), `ota_flow_init` inside the boot sequence (reason 1), and two calls whose only content is their *position* — `ota_flow_confirm_image()` early in the sleep funnel and `ota_flow_note_failsafe_sleep()` ahead of it on the failsafe path, with both verdicts belonging to host-tested `ota_flow.c`. `main.c` does not call `ota_flow_arm`, `ota_flow_check` or `ota_flow_apply` at all.

## RTC Persistent State

Declared with `RTC_DATA_ATTR` so values survive deep sleep — and *only* deep sleep, which the OTA reboot makes load-bearing (see the note below the struct):

```c
typedef struct {
    timer_state_t state;              // per-slot machine; only the ACTIVE slot can be RUNNING. BREAK is slot 0's alone and may be held there while ANY slot is active.
    int64_t       expiry_wall_time;   // Unix timestamp; 0 if unset. Set at IDLE->RUNNING and PAUSED->RUNNING; shifted by timer_shift_expiry() after the post-start NTP sync.
    int32_t       remaining_at_pause; // seconds saved on PAUSE/BREAK
    int32_t       allocation_sec;
    int32_t       run_accum_sec;      // screen-exposure balance (slot 0 only, whichever slot drives it)
    int64_t       run_started_wall;   // live segment start; 0 = nothing running
    int64_t       break_expiry_wall;  // 0 unless BREAK (slot 0 only)
    uint16_t      completions;        // runs that reached expiry today
} timer_slot_state_t;

typedef struct {
    timer_slot_state_t slots[TIMER_SLOT_COUNT]; // slot 0 = Screen, 1..TIMER_EXTRA_SLOTS = extra timers
    uint8_t       active_slot;        // Button C cycles enabled slots; rollover reverts to 0
    uint8_t       break_interrupted_slot; // slot selected when the break started; break end returns to it
    char          last_date[11];      // "YYYY-MM-DD"
    uint8_t       chore_acked;        // bit i = chore i ticked today (working copy; NVS `chore_ack` is the authority)
    bool          chore_released;     // latched: today's withheld Screen time has been granted
    uint8_t       mode;               // app_mode_t: Timers / Chores. RTC only — a restart comes back on Timers
    int64_t       next_ntp_sync;      // timestamp of next required sync
} rtc_state_t;
```

The three chore fields are day-scoped: `timer_reset()`'s one memset at the day
rollover clears the ticks and the release and puts the mode back to Timers.
Because `RTC_DATA_ATTR` does not survive an `esp_restart()` (see below), the
ticks and the release are also written to NVS on every toggle, and
`timer_persist_restore_chore_acks()` refills them at boot when the record is
today's.

(The authoritative definitions live in `include/timer.h` — check there first; this snapshot can lag.)

Extra-timer definitions (name/duration/reloadable/break-eligible) come from `MAGTAG_TIMER<n>_*` menuconfig symbols and live in rodata — `timer_defs_install()` must run each boot before any `timer_*` call (host tests inject their own table via `timer_set_defs()`). The single-timer API (`timer_start/pause/tick/...`) always operates on the active slot.

**State-model invariant (v1.4).** Only the active slot can be `RUNNING`, but `TIMER_BREAK` is decoupled from the selection: it lives on slot 0 only and may be held there while any slot is active, so a Screen Break enforces the *screen timer* without freezing the device. Every break helper (`timer_break_active/_remaining/_tick`, `timer_start_break`, `timer_shift_expiry`) therefore reads slot 0 explicitly, never the active slot. `include/timer.h` carries the authoritative version of this comment; `test/test_timer` encodes it as invariants I1–I5 in an `assert_state_legal()` helper that runs from `tearDown`, so every test in that suite trips on an illegal state.

Callers needing the break-end *edge* must call `timer_break_tick()` before `timer_tick()` — `timer_tick()` also ends an elapsed break (so no path can strand one behind a running extra timer), but silently.

**The screen-exposure balance (v1.5).** `break_eligible` is a per-timer flag meaning "this activity is time away from a screen". It has one consequence in two places: an eligible timer may be *started* during a Screen Break, and its RUNNING time *drains* the exposure balance instead of feeding it. Slot 0 is permanently non-eligible — screen time is the original non-eligible activity, which is what collapses the eye-rest counter and the break rules into a single quantity:

> Screen exposure is a signed balance on slot 0. Non-eligible RUNNING time adds 1:1, eligible RUNNING time subtracts 1:1, floored at zero. A break is due when it reaches the interval, and a Screen Break refuses to start any slot that is not `break_eligible`.

The balance lives on **slot 0 whichever slot is running**, so `timer_run_accum()` keys on slot 0's `run_started_wall != 0`, not on any slot's state — slot 0 is routinely IDLE or PAUSED while a chore timer drives it. The direction is **never stored**: it is derived at every fold from the running slot's `break_eligible`, so an HA edit of the flag cannot desynchronise from the balance. Three consequences worth knowing before touching `timer.c`:

- **Every transition into or out of RUNNING is a fold point** (I10) — start, pause, resume, expiry, a reconcile that renames/disables the slot, and a reconcile that flips `break_eligible` (which folds at the *old* sign, available only from `old_def`, since `net_apply` reinstalls the defs table before reconciling). Miss one and the balance either loses a segment or advances forever.
- **The floor is enforced twice**: at fold time and at read time, because the in-flight segment is not folded yet. A long eligible run must report 0, never a negative, to logging, HA and the break check.
- **Only two things reset it** (I9): a break start and the day rollover. `timer_start()` deliberately does *not* — a start that cleared it would let any timer press zero the eye-rest clock.

Idle neither adds nor drains. That is deliberate: the device deep-sleeps whenever nothing runs, so decaying through idle would mean the balance almost never survives to reach the interval, and "paused" is indistinguishable from "walked away".

`timer_break_due()` is gated on neither RUNNING nor slot 0's state — only on a break not already running. The balance can cross while Screen sits IDLE, an earned break is not un-earned by pausing, and eye rest must keep working after the day's allocation is spent: `EXPIRED` is the *normal* end-of-day state, and folding laundry with the TV on is exactly when a break still matters.

Break entry pauses whatever is RUNNING (I6), records `break_interrupted_slot` and `break_prev_state`, resets the balance and snaps the selection to slot 0. Break exit puts slot 0 back into `break_prev_state` (I7).

I6 holds **at entry only**: an HA edit flipping a RUNNING slot to non-eligible mid-break leaves it running behind the BREAK. That is accepted rather than prevented — the reconcile folds at the old sign and re-arms at the new one, so the exposure is counted correctly toward the next break, and pausing a running timer from inside a network window would be a much larger change than the case warrants.

**I7 is stored, not derived, and that is load-bearing.** Deriving slot 0's exit state from `remaining_at_pause` refunds the whole day in two ways, both reachable on a plain 60/30 config: an HA deduction landing *during* the break zeroes the banked value, so the exit reads as "never started" and hands back a fresh allocation; and an `EXPIRED` slot 0 used to carry a stale banked value from an earlier pause, so the exit handed that back instead. (`mark_expired` now clears `remaining_at_pause` — an expired timer holds nothing, which `timer_slot_remaining` already reported.) Deriving from `allocation_sec` instead fails too, because an HA deduction can zero that as well. The byte is free: the snapshot was already being versioned for `break_interrupted_slot`.

Likewise the live segment's sign comes from `run_segment_slot` — the slot that *armed* it — never from the selection. `run_started_wall` lives on slot 0, so nothing about the segment is recoverable from the selected slot, and the selection can move underneath it (`timer_ensure_active_slot_enabled` runs unconditionally on a snapshot restore). Since BUG-7 it first retires any RUNNING extra whose definition is gone, the way `timer_reconcile_def` handles a mid-window disable: the orphan's segment folds at the restore's `now`, non-eligible because its flag went with its definition, and the slot resets to IDLE with its completions kept. On the post-NTP rollover restore that `now` can follow a real power-off, so the dark time counts as exposure — bounded by the run's own remaining time, because an orphan that expired in the dark was already folded at its expiry. A PAUSED orphan is not reset, only deselected: a defs read failure or blob-version change installs the menuconfig table for one boot, and an HA-defined slot that table leaves empty would otherwise lose its paused timer. Both bytes ride the snapshot; restoring the arming slot as 0 would invert an eligible timer's drain into an accrual.

`test/test_timer` names its cases after the plan's behaviour-table rows (`test_row11_...`), so a failure points at the contract it broke.

The struct above is not the whole `RTC_DATA_ATTR` inventory. `main/lock_gate.c` keeps the four lock flags (`s_charge_locked`, `s_bedtime_locked`, `s_config_locked`, `s_clock_locked`); `main/display.c` keeps the previous-frame buffer and its validity flag, the partial/full cadence counter and the full-screen-takeover flag; `components/ssd1680/ssd1680.c` keeps a last-refresh timestamp for its refresh-rate guard plus its own previous-frame validity flag; and `main/wake_flow.c` (the two statics declared just above `wake_flow_note_sleep_entry()`) keeps the held-through-sleep guard — `s_held_mask_at_sleep` (which buttons were held at sleep entry) and `s_sleep_entry_time`. That last pair is RTC memory for exactly the reason the mechanism exists: EXT1 `ANY_LOW` is level-triggered, so the write happens on one side of a deep sleep and the read on the other, and without it a button still held when the release-wait times out re-wakes the chip and re-fires its action.

**`RTC_DATA_ATTR` survives deep sleep and nothing else — an OTA reboot zeroes all of it.** The bootloader loads the `.rtc.data` segment on every reset *except* a deep-sleep wake (the `load_rtc_memory = esp_rom_get_reset_reason(0) != RESET_REASON_CORE_DEEP_SLEEP` test in ESP-IDF's `esp_image_format.c`, cited at `main/display.c`), so the `esp_restart()` that ends an OTA commit brings every variable above back at its initialiser: `g_rtc_state` zeroed (the chore ticks and mode with it), all four `lock_gate.c` flags clear, `s_prev_fb_valid` and `s_takeover_on_panel` false, `s_last_refresh_sec` and `s_prev_frame_valid` gone with them, and `s_held_mask_at_sleep`/`s_sleep_entry_time` cleared too. `RTC_NOINIT_ATTR` is **not** the fix. The state has to cross into a *separately linked image*, and the mechanism that already does that — and that can *refuse* what it is handed, which no un-initialised RAM can — is the versioned NVS snapshot.

What actually copes is one injected call. `ota_flow_ops_t.persist_state` is `timer_persist_save` (wired in `main/main.c`), and `ota_flow_apply` calls it exactly once: after `session_end()`, so the flash write is not competing with the radio, and immediately before `restart()`. It is needed because `timer_persist_save` otherwise runs only at `enter_deep_sleep`, the **Bed Time** and **config-error** locks (`lock_gate_bedtime_engage`, and the engage branch of `check_config_error` in `main/lock_gate.c` — each has a save of its own *ahead of* its sleep, because it has just paused a running timer and wants that durable before a long lock; `lock_gate_check_charge` has no save of its own and is flushed by the same funnel like any ordinary path, which is why only those two locks are direct call sites), a break start and the expiry alert — every other path relies on the sleep funnel to flush eventually, and the OTA reboot never reaches it (`maybe_apply_update` sits ahead of the sleep in both wake tails). The sharp case is the primary trigger: on a rollover wake the pre-existing snapshot still carries *yesterday's* date, `timer_restore_snapshot` refuses it (it compares the blob's date against today and returns false on a mismatch), `g_rtc_state` therefore stays zeroed with an empty `last_date`, and `timer_is_new_day()` reads that as yes — so the new firmware would run the day rollover a second time and publish yesterday's summary computed from all-zero slots, permanently overwriting Home Assistant's record. Saving on this line instead writes a blob carrying *today's* date, which the post-OTA boot restores cleanly.

Two things about that save are easy to miss, and neither is decoration. It is also what keeps a rollback loop down to one attempt per day rather than a continuous one — `wake_flow.c` arms the OTA check inside the rollover branch *before* the in-rollover restore, so without a valid same-day snapshot every post-rollback boot would arm a fresh check, re-download, revert, and come straight back round with no sleep in between. And it works only because the wall clock outlives the reset that wipes `.rtc.data`: with `CONFIG_ESP_TIME_FUNCS_USE_RTC_TIMER=y`, ESP-IDF keeps boot time in the RTC retention *registers* rather than the `.rtc.data` segment, so `time(NULL)` is correct on the next boot and the snapshot is recognised as today's.

Everything else in the list above is benign across an OTA reboot, and it is worth knowing by *which* mechanism, because in one case it is not the obvious one. The post-OTA first paint is full because ssd1680.c's `s_prev_frame_valid` was wiped and `ssd1680_resolve_refresh_mode()` promotes the requested partial — **not** because of display.c's `s_takeover_on_panel`, which the same reboot also clears. A cleared lock flag simply replays the engage, exactly as after any hard reset. The held-through-sleep pair is benign for a structural reason rather than a lucky one: the guard only ever fires on a *deep-sleep* wake, and the reboot that clears it is not one, so a zeroed mask says "nothing was held" — which is the right answer for a boot that did not come out of a sleep. And `ota_flow.c`'s own buffered update is a plain static with no `RTC_DATA_ATTR` at all, deliberately: neither sleep nor reboot preserves it, so a forfeited update means "found again at the next check", which is at most a day.

## Subsystem Design Notes

- **Display stack**: LVGL 9 managed component (`LV_COLOR_FORMAT_I1`, clib malloc) over the custom `components/ssd1680` driver.
- **Refresh policy vs panel protection**: partial/full cadence (every 5th wake full, state changes full) is display.c policy; the ssd1680 driver independently enforces BUSY serialization + a 1 s minimum-interval guard (RTC-persistent) and puts the panel into RAM-retaining deep sleep (mode 1) after every refresh.
- **SNTP**: `esp_sntp` with `esp_sntp_set_sync_mode(SNTP_SYNC_MODE_IMMED)` set at runtime (the kconfig symbol was removed in IDF 6). `ntp_sync_in_session()` NEVER modifies `expiry_wall_time` — it corrects `time(NULL)` and the subtraction self-corrects. Exception: timer start/resume runs BEFORE the sync (immediate UX feedback); net_window.c measures the sync's clock step against the monotonic clock and whichever side reaches it first — `wake_flow.c`'s NTP-gated paint or `net_apply_finish()` — applies it via `timer_shift_expiry()`.
- **Partial-refresh ghost cleaning**: display.c runs every partial as a double pass — pass 1 writes the new frame with each dirty (column, band) segment inverted, pass 2 the true frame, starting the moment BUSY releases (no fixed inter-pass wait since c321ffc; the intermediate pass does not re-arm the driver's 1 s guard) — so per-wake text stays crisp between the every-5th-wake fulls. A changed pixel is driven once, as in a single partial; the *unchanged* pixels of a dirty segment are driven away and back, which is what clears accumulated residue. That is why the checklist gets the pass too: M2-T9 exempted chore→chore partials and the board showed ghosting, so M2-T15 restored it. Skipped when nothing in the bands changed, when `ssd1680_partial_diff_ready()` is false, and on a full refresh. Cost on glass is ~0.8 s — an *estimate* (two ~0.4 s partial waveforms), not a board measurement.
- **Deep sleep wakeup**: `esp_sleep_enable_timer_wakeup(55 * 1000000ULL)` + `esp_sleep_enable_ext1_wakeup_io(mask, ESP_EXT1_WAKEUP_ANY_LOW)` with RTC-domain pull-ups. Wake buttons only, per `wake_source()` in `main/buttons_policy.c`: B (14) and D (11) always outside the locks; C (12) when **either** of its two presses would succeed — `swap_allowed` (`timer_swap_allowed()`: extras configured AND active timer not RUNNING — a Screen Break deliberately does not refuse, so C stays a wake source right through one) **or** `chore_ack_allowed` (on the checklist with a second chore for C to tick). The locks override all of it: the config-error lock arms D alone (`config_locked` is checked ahead of every per-button rule), and the charge and Bed Time sleeps arm nothing (`enable` false, empty mask). **A (15) wakes conditionally** as of M2-T3, when its Timers/Chores toggle would actually be honoured — via `button_a_toggle_allowed()` (active slot not RUNNING **and** a chore list configured). That is the same gate the dispatch's A arm acts on, so the mask and the press can never disagree. The two conditional gates are kept *separate* on purpose even though both refuse while RUNNING: `swap_allowed` additionally requires extra timers to exist, and design 4.2 is explicit that the mode gate does not inherit that, so folding them would take the chore list away from every device with no extras configured. Note that on the fleet as it ships today — no chore list configured anywhere — that gate is false and A is armed on nothing, which is the intent: the feature costs no wakes until it is used. B is armed unconditionally despite a few states refusing it (an expired non-reloadable slot; Screen during a break) — a deliberate overshoot, because the failure is asymmetric: a needless wake costs one refresh, whereas an under-armed B makes the primary control dead to the press with no way to tell that from a flat battery. The mask itself is `buttons_policy_wake_mask()` — pure and host-tested — and is rebuilt at every sleep entry, so it tracks the state machine. A non-wake button is also left *unconfigured* in the RTC domain: an open button on an isolated pad draws nothing, where a pull-up would leak ~70 uA while held. `buttons_get_wakeup_button()` reads the EXT1 status latch first, which can only ever name an armed pad; its fallback level scan (latch empty) is bounded by the policy's **maximal** mask — every gate open — so a pad no gate could ever arm cannot be blamed for a wake, and the bound is derived from `buttons_policy.c` rather than hardcoded, so it follows the policy automatically. What that bound does **not** do any more is settle *which* of two held pads fired. It used to, by accident: it excluded A outright, so a wake genuinely caused by B, C or D while A happened to be held could not be misreported as A. A is in the maximal mask now (the mask asks "could any gate arm this?", and A's gate can), so with two pads held the lowest index would win again — and A is index 0. That is why the scan resolves through **`button_latch_pick`** rather than returning the first held pad: the same pure, host-tested B > C > D > A policy the two latch drains use, so the tie-break exists in exactly one place. Ordering it is not merely tidy. The maximal mask is *counterfactual* — it assumes every gate open — while the mask that actually armed the sleep was the real one, and on a device with no chore list A's gate is false. A held A on such a device provably could not have caused the wake, yet an index-order scan would still return it, the toggle would be refused by its own gate, and the real B press would be gone: the "primary control dead to the press" failure this policy is otherwise built to avoid. `buttons.c` has no host suite — nothing compiles that TU without ESP-IDF — so its four seams rest on review, and they are named in its header comment. (`esp_sleep_enable_gpio_wakeup()` is light-sleep-only on ESP32-S2.)
- **WiFi lifecycle**: one bounded network window per sync, run on a dedicated `net_win` task (`main/net_window.c`): wifi_session_begin → SNTP → snapshot rendezvous → MQTT/HA session (best-effort, skipped when broker URI empty) → wifi_session_end. WiFi is off outside windows. The task never mutates timer state, paints, or touches LEDs — it signals NTP-settled (with the measured clock step) and window-done; grants/bonus/locate are buffered by mqtt_ha and applied by `net_apply_finish()` (host-tested `main/net_apply.c`), which also re-installs the timer-defs blob and runs `timer_reconcile_def` on every extra slot redefined mid-window (only the active slot drives sound/display). A start/resume that painted before the sync settled is marked via `net_apply_note_start_unsynced()`; if the sync lands during the MQTT tail, the finish applies the measured clock step to the expiry (`net_window_take_clock_step()` is consume-once, so the paint-time and finish-time paths can never double-apply). Interactive wakes (BTN B start/resume, BTN D on the timer screen) paint once NTP settles while MQTT drains behind the panel — no other button opens a window, and in particular a chore tick (B/C/D on the checklist) does not, so HA hears about it at the next window rather than at the press; unattended wakes use the blocking `net_apply_try_window()`. `enter_deep_sleep` joins any straggling window (bounded) before sleeping.
- **Firmware update — two windows, and the paint between them**: a *check* is one small HTTPS GET of the manifest riding the window the wake was already opening (`ota_flow_check`, on the `net_win` task); a *download* is a second window, opened only on the days an update actually exists (`ota_flow_apply`, on its own `ota_dl` task, after the first window has closed). The split is load-bearing, and the panel is the reason: `display_ota()` carries no `net_window_active()` guard and its flush blocks for a full refresh, so painting inside an open window walks into the brownout this project already paid for once. Window 1 closes → paint → window 2 opens, and `ota_flow_apply` enforces that by owning both the paint and its own `session_begin` rather than trusting the call site (`test_ota_flow` asserts it). The check's placement inside window 1 is equally deliberate: it sits after the snapshot rendezvous, which has already blocked until the wake's paint finished — so the panel is idle when the check transmits, with no new mechanism needed — and before `mqtt_ha_window`, so this check's verdict is in hand when the stat payload is built. Which wakes check is `ota_flow_arm`'s answer rather than the call site's, because it depends on a runtime flag only NVS knows: a day rollover always arms one, a Button D full sync arms one only when `ota_on_sync` is set, and a tick wake, break end or final-minute sync never does. Effects cross the task boundary the way every other network→device effect here does — the check *buffers* the version and URL it found, and the main task reads it only after `net_window_join()`. The battery and charge-lock facts are sampled on the main task and sampled **again** before the download, because the two windows are minutes and a full-panel repaint apart and a cell that crossed into the charge lock in between is exactly the one that must not be asked for a sustained radio burst followed by a flash write.
- **The download's two budgets, and why they are two**: left alone, a link slow enough for the transfer to outlast `CONFIG_MAGTAG_MAX_AWAKE_SEC` (180 s) would have the awake failsafe fire mid-transfer and deep-sleep the device with no abort, no `ota_result` and nothing observed. So `ota_flow_apply` re-arms the failsafe for `CONFIG_MAGTAG_OTA_MAX_SEC` (default 300) **plus an abort tail**, while giving its own download loop `max_sec` exactly, both anchored on the same line: the loop is then guaranteed to stop the transfer first, with time left to run `dl_abort` and `session_end`. That the tail actually covers those is arithmetic rather than hope — `include/ota_timing.h` holds the per-socket timeout, the OTA read-buffer size and the tail together, and `_Static_assert`s that the tail exceeds one worst-case `dl_step` plus `dl_abort` plus `session_end`; the two constants used to live in two files and were compatible only by coincidence. The loop is also why the transport is four calls (`dl_begin`/`dl_step`/`dl_finish`/`dl_abort`) instead of one `esp_https_ota` call: the deadline check lives between the steps, and "the deadline aborted it and never switched the boot partition" is then a host assertion rather than a comment. Counting arms, the failsafe is re-armed **four** times in `ota_flow.c` (every `s_ops.extend_awake` call — named by role rather than line number, because the numbers that stood here had drifted), and the fourth is the one a reader is most likely to delete as redundant: `ota_flow_apply()`'s first arm is the up-front gate described below (`awake_sec`), its second is the download's own anchor (`max_sec` + the abort tail), `fail_attempt()` puts an aborted wake back on an ordinary `awake_sec` budget — and `ota_flow_apply()`'s last arm re-arms for `awake_sec` again *after* the loop and *before* `dl_finish`, which is the only thing that gives the **commit tail** a budget of its own. `ota_timing.h`'s `_Static_assert` justifies its tail in abort-path terms only (one worst-case `dl_step` + `dl_abort` + `session_end`); the commit path is the more expensive of the two and none of it is covered by that assertion — `esp_ota_end` → `ota_verify_partition` is a full ~1.5 MB SHA-256, `esp_ota_set_boot_partition` → `image_validate()` is a *second* one, and an `otadata` erase-and-write plus three NVS writes follow. Note that that last arm does not *extend*: it is absolute-from-now, so a download that finished quickly walks away with `awake_sec` where it had minutes left. That is deliberate, the comment above the line says so at length, and it must not be "fixed" back — losing the commit-tail race is the one outcome in this firmware that yields garbage rather than zeros, because a failsafe sleep landing between `esp_ota_set_boot_partition` and `restart()` makes the next boot a deep-sleep *wake of the new image*, the one reset the bootloader does not reload `.rtc.data` for. What the deadline does **not** bound is likewise stated rather than implied, and `dl_begin` alone is two unbounded loops rather than one: `esp_https_ota`'s `_http_connect` is `do { open; fetch_headers; handle_response } while (redirect)` with no hop counter of any kind, and *separately* its `read_header` retries `ESP_ERR_HTTP_EAGAIN` inside a loop with no cap, so a peer that sends headers and then stalls spins there at one socket timeout per turn with no redirect involved. Only the first has a lever: `main/ota.c`'s `kill_this_transfer()` closes the client from inside the HTTP event handler when `ota_url` refuses a redirect, which makes the in-flight `fetch_headers` fail and ends that loop — **nothing** bounds the stalled-header one, and a brownout or a battery pull is unbounded everywhere. What covers all of them is the retry budget being charged **before** the attempt: `ota_fails` and `ota_target` are written to NVS ahead of the first byte, so an attempt the failsafe kills mid-flight is still counted on the next boot. The budget is keyed on the target version (`CONFIG_MAGTAG_OTA_MAX_FAILS`, default 3, and a caller that passes 0 gets the default rather than "unlimited"): a *different* version resets the count, which is the escape from a daily sad loop — publishing a new version re-arms the device, with no reset needed from anywhere else — and an exhausted budget stops with a visible `gave_up` rather than silently. The extension is therefore asked for **first**, ahead of the paint and ahead of the charge, and its answer is believed: main.c only *logs* a failsafe create/start failure and the extender then null-guards for the rest of the boot, so if `extend_awake` answers false `ota_flow_apply` declines the attempt outright — nothing painted, nothing charged — rather than starting something nothing could end.
- **OTA reporting, and why it is read at publish time**: the two windows report differently. A check failure publishes in the window that produced it; a download failure cannot — MQTT is already closed by then and reopening it would cost another association — so it is persisted to NVS and published in the *next* window. Success needs no report at all: the device reboots and announces itself through the new version in the stat payload's `fw` field and on the panel. The four device-owned keys behind that (`ota_result`, `ota_target`, `ota_fails`, `ota_dl_ms` — none of them has a bulk-document key, because none is operator config) reach Home Assistant as `ota_stat_t`, a separate argument to `stats_json_stat` rather than four more `stats_snapshot_t` fields, and `ota_flow_stat()` reads them from NVS **at publish time inside `mqtt_ha_window`**. That is not a preference: `stats_snapshot_t` is filled by `stats_collect()` on the main task and posted to the network task by value, which copies it off the queue *before* it calls `ota_flow_check()` — so an OTA field carried in the snapshot could only ever publish the previous wake's result, and keeping these four out of it makes that mistake unrepresentable. `ota_dl_ms` has a second reason to come off flash: the download runs in a window that closes before MQTT opens and its success path ends in `esp_restart()`, so a RAM copy is structurally always zero. Which reason codes may overwrite `ota_result` is one rule in one place (`ota_policy_reason_is_persistable`, pure and host-tested): the rows where no check ran leave it alone, so an earlier window's genuine failure is not overwritten by a routine skip.
- **Rollback, and the one wake an image gets to prove itself**: `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y`, so a freshly committed slot boots as `PENDING_VERIFY` and the bootloader marks it aborted and boots the other slot unless the app cancels the rollback during that boot. `CONFIG_BOOTLOADER_SKIP_VALIDATE_IN_DEEP_SLEEP` stays **off**, so a deep-sleep wake re-runs the 2nd-stage bootloader like any other reset — which makes every wake a rollback opportunity and gives a new image exactly *one* wake to certify itself. That is why the call sits in `enter_deep_sleep()`, the single funnel every sleep passes through including the lock gates and the early-out sleeps, and not at the two wake tails where the *apply* lives; the contrast is the design rather than an inconsistency, because skipping an apply defers an update by a day while skipping a confirmation reverts one. The awake-failsafe path deliberately declines to certify, and announces itself with `ota_flow_note_failsafe_sleep()` on its way into the funnel rather than being inferred there: if a new image's first wake had to be killed, that is the strongest evidence anyone has that the update is bad, and the accepted cost — a one-off wedge throwing away a good update, which is then re-found and re-downloaded — is the direction to be wrong in on a board with no UART bridge chip. A revert is detected on the boot that comes back, from `ota_flow_init` (early enough that the verdict reaches the same wake's stat payload) and from a **one-shot token**: `ota_pend_ver` holds the version the commit wrote and is consumed by whichever future arrives first — certification, or a boot running something else, which records `rolled_back`. A token rather than a pair of levels because "the other slot is aborted" and "`ota_target` names a version we are not running" are both *states* that stay true indefinitely and would latch a month-old rollback over every later result. And the token carries the committed version itself rather than sitting beside `ota_target`, because `ota_target` means "what the retry budget is counting" and is re-pointed before every attempt — two meanings that diverge the moment any attempt happens between a commit and its revert, which is the ordinary case rather than the exotic one.
- **Config channels — the durability rule**: two channels write HA-managed config and they are deliberately asymmetric. The retained bulk `config` document (`main/config_apply.c`) is durable on the broker and reapplied whenever its `ver` differs from the stored `cfg_ver`. The per-entity retained `set/<key>` commands (advertised `"retain":true` by `main/ha_config.c`, applied by `apply_sets()` in `main/mqtt_ha.c`) are **consumed on apply** — the retained command is cleared so a stale set cannot re-override the document every window. That asymmetry forces an invariant on every new field: **anything settable from an HA entity must also be expressible in the bulk document**, because an entity-only field then has no durable store anywhere and is destroyed the next time the document applies. Concretely, when adding a field to timers 1–4, ask *"is this durable config that belongs in HA?"* — the answer is almost always yes, and if it is, the field must be (1) parsed from the bulk `timers` entry, (2) documented in `docs/home_assistant.md`, and (3) published in the state JSON so HA's UI mirrors what the device actually believes. `break_eligible` shipped with the entity and the parser but not the schema or the docs, so every application of a documentation-shaped document silently cleared it. Hence the optional-key rule: within a `timers` entry an omitted `reload`/`break` means *leave the stored value alone* for a slot that already exists, and false only for a slot the document defines for the first time. The rule runs one way only: it does not require every document field to have an entity. `holidays` and the chore list (`chores`) are **document-only** — no registry row, no `set/` key — and the four `chore_free_*` are ordinary registry fields that the document also carries. One deliberate divergence between the two channels: for a `chore_free` pair the per-entity setters refuse or clamp, while the bulk applier names a broken pair in the ack and leaves it standing (the config-error lock needs something to fire on).
- **Two-event sleep planning**: because a Screen Break keeps running behind another selected timer, a wake can have two future events — the active timer's expiry and the break end. `sleep_plan_in_t` carries the break as an optional *secondary* event (`break_remaining_sec`) with the same `SLEEP_PLAN_EVENT_LEAD_SEC`; it only ever pulls the wake in. `sleep_plan_from_timer()` populates it **only when the end will actually chime** (`break_active && state != TIMER_BREAK && !extra_running`): a suppressed end is silent, so it needs neither a dedicated wake nor a stay-awake watch and simply drops the header chip at the next tick wake. Suppression can only change via a button press, which is a wake and therefore a re-plan. `enter_deep_sleep` supplies only the seven raw timer readings (`sleep_plan_timer_in_t`, all side-effect-free getters, all taken unconditionally); the fold — which reading each state uses and when a background break earns its own wake — is all decision and no device, so it sits with the planner and is host-tested there.
- **Break-end edge**: the transition is **latched** in timer.c, not returned: `timer_tick()` ends an elapsed break internally, so an edge reported only as a return value could be consumed by any tick and the chime silently lost (it was — the expiry alert's tick swallowed it). `timer_break_tick()` latches the break's wall end; `timer_break_take_ended(now, &overdue)` consumes it exactly once, reporting how late *the drain* is. Ordering therefore stops mattering: tick whenever, drain whenever. `wake_flow_break_end()` (`main/wake_flow.c`) is the single owner of the policy — it ticks then drains (both halves idempotent), applies `wake_policy_break_chime()` (pure, host-tested), chimes only when nothing else is RUNNING *and* the drain is within `BREAK_CHIME_GRACE_SEC` (= `SLEEP_PLAN_WATCH_SEC`, 75 s: charge/bed-time locks and power cycles can span the end, and the chime is an "it just happened" signal, not a replay), and on chiming also calls `timer_select_interrupted()` — the chime and the return to whatever the break interrupted are one event, and it is not necessarily Screen, since a break can be earned entirely by a non-eligible extra. It sets a wake-sticky flag (`wake_flow_break_ended_this_wake()`) passed to `wake_policy_render` as `break_ended`, which forces a full refresh because the panel changed (chip gone, possibly a different timer's layout) even when `before == after`. It runs at the top of both wake handlers (after rollover + bedtime, before `before` is captured, so the snap is invisible to the state diff) and at a **guaranteed drain** in wake_flow's `maybe_wait_for_event()` — the one point both handlers reach after all timer work and before sleep. The repaint variant `wake_flow_break_end_repaint()` drains *before* it paints, never after: the paint reads the active slot, and a drain that snaps the selection back changes which slot that is. Finally `enter_deep_sleep()` calls `wake_flow_report_undrained_break_end()`, which logs a warning if a latch ever arrives there undrained — a deliberately *raw* take rather than the owner above, because by then the panel is finished and the network task is gone, so the tick, chime, snap and sticky flag would all land where nobody could see them (and it can run from the failsafe's `esp_timer` context, where audio is not safe). What stays in main.c is only the call's **position**: it has to sit after every path that could have drained the edge, or "undrained" would mean nothing.
- **Awake press latch**: buttons are dispatched on EXT1 wake; while awake a NEGEDGE ISR latches presses (button_latch.c, pure and host-tested) and wake_flow's checkpoints consume them — A, B and C act on a latched press, through the same guard matrix as a wake press (`wake_flow_dispatch_button_action`), so a press that landed during the sync, the grid wait or an e-ink flush is not lost. **D is in the pick only in chore mode** (M2-T4b, `wake_flow_pick_latched_press()`), where it is ✓3 and has no network leg; outside chore mode it is excluded from the *pick* rather than from the take, so a latched D is taken and dropped — its timer-screen job opens a network window, and a D that merely rode in on another wake must not buy one. The shared dispatch still has no BTN_D arm: a latched ✓3 routes through `wake_flow_dispatch_latched_press()`, and the EXT1 decode keeps its own D binding (sync on the timer screen, ✓3 on the checklist). **A is in both pick masks** as of M2-T3 — it has a binding now, and what makes admitting it safe is its position *last* in the pick order (below). The narrow polls during a network-window join (`wake_flow_poll_button_b_action`) and inside the final-minute watch (`wake_flow_poll_pause_button`) mask down to B alone, and the join poll leaves B latched in chore mode rather than applying its timer action — except under any lock, and after a release until the repaint replaces the lock screen, where it takes B and drops it in either mode (M3-T4; see the config-error lock below). A chore gesture has its own consumer: `wake_flow_coalesce_chore_acks()` holds the paint open for a sliding quiet window (`CONFIG_MAGTAG_CHORE_PAINT_QUIET_MS`) inside one per-wake budget (`CONFIG_MAGTAG_CHORE_ACK_BURST_MS`) and takes every ack and any A pressed in it, and `wake_flow_repaint_chore_acks_until_quiet()` takes the acks made during the refresh itself. What the latch cannot catch is a press made before `buttons_init()` arms the ISR, well into boot — a second button tapped while the first press's wake is still booting is lost (M2-D1, deferred).

  The pick order is *"the time-sensitive action wins"*, not "the lowest index wins": `button_latch_pick` runs B, C, D, A. That list moved when the layout did. Leaving A at the front once it lost its binding let an unbound button **swallow** a real press — pick returns the first candidate in order, so A won, its dispatch arm did nothing, and the B press beside it was gone with it, consumed by the same unmasked take and dropped at sleep.

  Two guards used to stop that: the order, and A's absence from the allowed mask. **Only the order remains.** M2-T3 gave A a binding and admitted it to both pick masks, which spent the second guard — so the priority list is now the *sole* thing keeping a mode toggle from swallowing a start press latched beside it, on both drain paths. Treat `priority[]` in `button_latch.c` accordingly: reordering it to put A (index 0) first, on the reasonable-sounding belief that the masks still cover this, re-creates the original bug in full — every start press latched next to a held A disappears, which in the field is the device's primary control appearing dead. `test/test_wake_flow/test_wake_flow.c` pins this and says the same thing at the assertion; the two must not be allowed to drift apart again. ISR handlers detach in `buttons_configure_wakeup_if()` before the pads move to the RTC mux; held-button logic stays level-based.
- **Awake failsafe**: a one-shot esp_timer (`MAGTAG_MAX_AWAKE_SEC`, default 180 s) forces a snapshot-preserving deep sleep if a wake wedges (WiFi hang, stuck BUSY) so the battery cannot drain. main.c owns the handle (there is no module home for an esp_timer) and installs `extend_awake_failsafe` into alerts.c via `alerts_set_extend_awake()` at boot, so a deliberately long awake stretch — the locate alarm — can push the cap out: *how long* is alerts.c's decision, *applying it* is the handle owner's.
- **Battery charge lock**: `lock_gate_check_charge()` runs in `app_main` before the wake decode — <=10% pauses a RUNNING timer, paints Charge Me! once, sends one last best-effort stat, drops button wake sources, and sleeps 600 s battery-recheck intervals; releases >15% (battery_policy.c hysteresis). All four locks are RTC flags in `main/lock_gate.c` and all four end the wake by calling `enter_deep_sleep()`, which is why `lock_gate.h` is where that function is declared. A wake that *releases* any of them is still facing a lock screen on the panel, so `lock_gate_promote_render()` promotes that wake's partial to a full refresh.
- **Bed Time lock**: `lock_gate_check_bedtime()` runs in both wake handlers right after day rollover (policy in host-tested `main/bedtime.c`; the gate itself in host-tested `main/lock_gate.c`). At/after the configured HHMM (default 2200; 0 disables; validated to 0-or-1800–2359 so a bad edit can't daytime-lock the device) it pauses a RUNNING timer, paints the inverted Bed Time screen once, alerts audibly only when it interrupted RUNNING or a break — `bedtime_should_alert(state, timer_break_active())`, since the break may be running behind a different selected timer, and a pending screen break that would cross bedtime skips straight to Bed Time — then sleeps charge-lock-style: no button wakes, fixed 7200 s intervals that only run a net window (NTP + HA config pickup — a bedtime edit applies at that same wake) and re-check the gate. Day rollover clears the lock; the flag is RTC-only, so a hard reset just replays the engage. A clock that was never set is not judged at all: after a power-on reset the clock reads near the 1970 epoch until NTP lands. The power-on's day-rollover window normally syncs NTP before the gate runs. When it does not, the no-clock lock (below) ends the wake before bed time is reached, so the bed-time skip — when `time_util_clock_plausible()` (`include/time_util.h`, floor 2026-01-01 UTC) says no, bed time neither engages nor releases — is now a belt inside `check_bedtime()` rather than a path. The break planner's bed-time crossing (`wake_flow_maybe_start_break()`) asks the same question, so an unset clock cannot raise the flag the skip holds. The replay then happens on the first wake after NTP works, which can be hours later: a device that lost power and has no WiFi does not enter bed time until it syncs. Without this, a time zone that puts near-epoch local time inside the window would lock the device for 7200 s on a clock nobody had set (BUG-11).
- **No-clock lock** (BUG-14, owner decision 2026-09-25): `check_clock()` in `main/lock_gate.c` runs FIRST inside `lock_gate_check_bedtime()`, ahead of bed time and config error, because both of those read the clock. **Trigger:** `now` fails `time_util_clock_plausible()` — a power-on whose rollover window could not reach NTP. **On engage** it paints its own screen (`display_no_clock()`: No Clock, check WiFi, no screen time until it syncs, press D to retry; golden `no_clock.bin`) and sleeps, with no window of its own (the rollover's has just failed). **What it blocks:** everything but D — no screen time is handed out, and the stand-in day the rollover dated `1970-01-01` is never usable. It sleeps the config-error lock's sleep (`lock_gate_sleep_mode()` folds the two flags into `WAKE_SLEEP_CONFIG_ERR`: `CONFIG_ERR_SLEEP_SEC`, and `lock_gate_wake_d_only()` tells `buttons.c` to arm D alone; the sleep log reads `config/no-clock lock`), so every 30 min, or at once on a D press, a locked re-wake runs one `net_apply_try_window_then(clock_after_ntp)` — the retry — and repaints if the clock is still unset. There is no give-up: WiFi that works with NTP (UDP 123) blocked keeps it locked indefinitely, retrying on that cadence (owner decision Q3). **Clears** when the clock is plausible. The usual release happens inside the retry window, in the after-NTP hook, which runs after the sync and before the stats snapshot the window's MQTT phase waits on: `settle_day()` restores today's snapshot over the stand-in day (`timer_persist_try_restore()`), or, with none for today, resets to a fresh today and queues the retained HA bonus target's clear; then the NTP-sync record the reset wiped is put back. So that window's stat is the real day's, and the commands it picks up land on the real day. It also releases when the clock is found set before the window (an async sync between wakes) or after it (a sync that settled during the MQTT tail); both settle the day the same way, after any window of the wake has posted its stats, so a day settled there owes one more window (owner decision Q-B). `lock_gate_check_bedtime()` pays it last, unless the bed-time engage or the config gate has already opened a window of its own in that call; it carries the fresh day's bonus clear, which is plain RAM and would otherwise die at sleep, and the commands the locked windows held. When its NTP succeeds it records the sync, so a tick wake's sync block adds no window after it. Every release returns `true` like the other releases, so the press is the lock's and the repaint is full. **Day-scoped HA commands wait for it** (owner decision Q1): while the clock or the RAM day is unset, the stats snapshot carries `no_clock`, and `mqtt_ha` leaves a `cmd` grant (`cmd_apply_for_snapshot()` → `CMD_HELD`, id not recorded) and a `set/screen_bonus` target retained, unapplied and unacked, and publishes no bonus clear. A clear refused that way is dropped, not deferred; each path that then starts a fresh day queues a new one: the release (above), and the power-on rollover whose NTP landed after its window's stats post, on its reset branch (`wake_flow_handle_day_rollover()`; the reset wiped the sync record, so the tick's sync block carries it). Those decisions are pure functions in `main/ha_day_cmds.c` (`test_ha_day_cmds`), because `mqtt_ha.c` is in no host suite; with a day settled and a clear pending, a target is dropped, so a target set during the lock does not survive a release onto a new day (owner decision Q-A). Config documents and settings still apply. **The day rollover stands aside** while the lock holds a stand-in day (`wake_flow_handle_day_rollover()`), so the stand-in's own "midnight" opens no second window and queues no clear; the gate settles that day. **A running timer is not paused:** the real day is not in RAM, so a restored RUNNING slot has drained in wall-clock time through the outage and the lock, like any power loss, and may come back EXPIRED; a release on a later day starts fresh (owner decision Q2). Charge lock outranks it (sleep precedence). Known gap, low harm: the release wake arms no daily update check (it slips to the next midnight). The belts behind it stay: `timer_persist_save()` never writes a stand-in day, the chore-ack record is never stamped 1970, the rollover sends no summary for it, and the HA stat reports `state: NO_CLOCK` with nothing remaining while the clock or the RAM day is unset (`app_state_stats()`).
- **Config-error lock** (chore checklist, design 5.3): the third lock added, and the only one a configuration mistake can trigger. `check_config_error()` in `main/lock_gate.c` runs straight after the Bed Time check, inside the same `lock_gate_check_bedtime()` call, so it is reached from both wake handlers after day rollover. **Trigger:** today's stored `chore_free_*` exceeds today's allocation — judged on the **raw** minute pair (`schedule_get_chore_free_pair_min()`, not the clamped `schedule_get_chore_free_sec()`, after which no pair could ever fail) with the shared `config_is_valid_chore_free_min()` predicate, and on **today's** day type only, resolved again after the window so a clock step or a day change is honoured. The HA per-entity setters refuse (`chore_free_*`) or clamp (allocation) so they cannot create the pair. Two routes can: the bulk document, because `config_apply.c`'s `check_chore_free_pairs()` names a broken pair in the ack but deliberately leaves it standing; and a defaults reseed, because `reseed_all_defaults()` (`main/nvs_config.c`) rewrites the four allocations (`NVS_SEEDED_U16S`) to their Kconfig values while the lazily-created `chore_free_*` keys survive — no document, no ack. The reseed also clears `cfg_ver`, so the retained document re-applies in the next window and heals the pair if it carries the allocation. **On engage** it pauses a RUNNING timer, runs `timer_persist_save()`, and paints Config Error naming the pair *before* the window. **What it blocks:** everything but Button D — the EXT1 mask is D alone (`buttons_policy.c` checks `config_locked` ahead of every per-button rule) — and every wake, engage or re-wake, runs one `net_apply_try_window()` (the only remote fix path) and then re-checks. **Clears** when the re-check passes: a fixed pair (HA control edit or a new document), or a day type whose pair is valid; the wake falls through to the normal flow, which repaints fully. `lock_gate_check_bedtime()` returns `true` on any release (any of its three locks, before or after the window), and that is what makes "fix it in HA, then press D" exactly true: the press that woke the device is **consumed** — the button handler runs no action for it, so D neither ticks chore 3 nor opens a second window with an update check — and every press made before the repaint replaces the lock screen belongs to the lock too, including one made *after* the release: the tick handler's regular sync and grid wait can hold Config Error on the glass for tens of seconds after the gate let go. `s_lock_screen_on_glass` (`main/wake_flow.c`) marks that span: both handlers raise it on a release and the repaint clears it. The button handler's tail drain empties the latch before its first render, which that flag forces full (the path never asks `lock_gate_promote_render()`); the tick handler drains the latch right after its render (promoted by the gate) and before its own latch pick, so a D pressed during the grid wait cannot reach ✓3. The join poll (`wake_flow_poll_button_b_action()`) drops B under every lock, because each lock's window joins with its flag already set, and while the flag stands; the grid wait's pause poll already takes B and acts only on a RUNNING timer, which no release leaves behind. A config-locked D wake in chore mode does not claim the LED strip (the chore colours would sit over Config Error for the whole window and stand the sync pixel down); after a release that wake's checklist gets the timer-state paint, as a tick wake's does. Otherwise it repaints its own screen (the last word on the panel) and sleeps `CONFIG_ERR_SLEEP_SEC` (1800 s, `include/sleep_plan.h`) with D armed. A broken pair on another day type does not engage it (row C12); `schedule_chore_free_broken_mask()` reports it to HA's `config_warning` sensor instead — recomputed into every stats snapshot (`app_state.c`) and so published in every network window.
- **The device locks — four, in precedence order.** `wake_sleep_mode_select()` (`main/sleep_plan.c`) ranks the sleeps charge > Bed Time > config error; the no-clock lock is folded into the config-error sleep (`lock_gate_sleep_mode()` passes `s_config_locked || s_clock_locked`). Inside `lock_gate_check_bedtime()` the gates run no clock → Bed Time → config error, and a no-clock lock ends the wake before the other two are reached. Each paints its own screen and owns the sleep:

  | Lock | Trigger | Blocks | Sleep / buttons | Network window | Clears |
  |------|---------|--------|-----------------|----------------|--------|
  | Charge | battery ≤ 10 % | everything | 600 s, no button | engage wake only | battery > 15 % |
  | Bed Time | configured HHMM reached | everything | ~7200 s, no button | every wake, engage included | day rollover, or a bedtime edit / clock step |
  | No clock | unset clock after a power-on whose first NTP failed | everything but D, which retries at once | 1800 s, D armed (the config-error sleep) | every re-wake, not the engage | the first NTP sync; the day is settled before that window's MQTT phase |
  | Config error | today's `chore_free` > today's allocation | everything but D, which only brings the re-check forward | 1800 s, D armed | every wake | the pair validates |

  Each released-flag (`s_*_released`, "repaint over the lock screen") is a plain RAM static, so a wake that releases and then takes an early-out sleep before rendering can leave the lock screen on a healthy panel until something else forces a full refresh; and `RTC_DATA_ATTR` does not survive `esp_restart()`, so an OTA reboot or panic replays the engage (idempotent — one more paint and persist). One RTC-backed mechanism for all four is deferred (M2-D4). A device both config- and charge-locked has neither a button nor a network exit until the battery recovers.
- **Discovery republish**: HA discovery documents are republished when `STATS_JSON_DISC_SCHEMA_VER` (`include/stats_json.h`) moves — a new or renamed entity, or a changed discovery payload — **or** when `ha_config_discovery_hash()` (`main/ha_config.c`) moves. That 16-bit fingerprint folds the three inputs discovery depends on that the schema version cannot see: the `dev` block's mutable fields (device name and firmware version, `ha_config_device_hash()`), each extra-timer slot's name and enabled bit, and the chore list (count, then each name — the `chore_N` binary sensors are named `"<name> done"` and rows past the count are retired). A device with no chore list folds nothing for it, so it hashes exactly as it did before the feature. `ha_config_discovery_gate()` reads the chore list **once** per window, fingerprints exactly that, and returns both whether to publish and whether the result may be stamped: an **unreadable** list skips every chore row (neither renamed nor retired on a guess) and withholds the stamp, so the pass is retried every window until a read succeeds. `mqtt_ha_window()` publishes discovery and the stat payload *before* `apply_incoming()` applies the config document, so a list change applied in window *N* reaches HA in window *N + 1*.
- **Alert tones**: alert audio is DAC-synthesized (`main/tones.c` note tables + envelope renderer, host-tested; `main/audio.c` pumps `dac_continuous` DMA on the S2's DAC CH0 = GPIO17) with per-alert tone selection (expiry/break/bedtime) stored in NVS and exposed as HA selects, plus a global alert volume (NVS `alert_vol`, HA number, 0–200 %: 100 % = the gentle reference amplitude, above that the renderer/WAV downmix apply digital gain clipped at the DAC rails for real loudness on the small speaker; menuconfig default 200). "Custom WAV" streams 16-bit mono PCM (8–22.05 kHz) from the raw 440 KB `assets` partition (`tools/flash_assets.sh`), falling back to the chime when absent/invalid.
- **Display golden tests**: `test_display_render` compiles vendored LVGL for the host (`test/mocks/lv_conf_host.h`) and byte-compares each screen against `test/test_display_render/golden/*.bin`; regenerate intentionally changed layouts with `MAGTAG_WRITE_GOLDEN=1`.
- **NeoPixel power gate**: GPIO 21 must be HIGH (off) on every boot/wake before any other peripheral code runs.
- **IDF 6 component names**: the `driver` umbrella no longer pulls the peripheral drivers in, so each is named in `REQUIRES` — `esp_driver_gpio`/`esp_driver_dac`/`esp_driver_rmt` for `main`, `esp_driver_spi`/`esp_driver_gpio` for `components/ssd1680`.
